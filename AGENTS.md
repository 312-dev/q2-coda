# Vamp: index for agents

`CLAUDE.md` is a symlink to this file. It is an index: follow the links, don't expect the detail here.

## What this is

Vamp is GPL-3.0 custom firmware for the Shanling Q2 music player, made by patching Shanling's stock V1.36 firmware, never by rebuilding it. `tools/build.py` takes the stock ZIP, checks its hash, and changes two stock programs in place, `demo` (the AWTK UI) and `bluealsa`, and replaces the player, `hciplayer`, with Vamp's own `q2player` (`player/`). Checked MIPS prologues at stock addresses (`HOOKS` in `tools/build.py`) jump into a payload compiled from `patch/*.c` and mapped at `0xb00000` in `demo`; single instruction words are swapped where a hook is too much; and stock's UI assets (pages, styles, strings, icons) are rewritten at build time by `tools/ipod.py`, `tools/theme.py` and `tools/art.py`. The output is an `update.tar` the stock updater installs. Shanling's files are never in the repository.

Read [docs/architecture.md](docs/architecture.md) first (20 minutes: the payload's layout and limits, how C calls stock, hooks, where to start per kind of change), then [docs/source-map.md](docs/source-map.md) (every file, one line each).

## Commands

Security scan (code, secrets, dependencies, firmware): `python3 tools/scan.py`, see [docs/building.md](docs/building.md#security-scan).

Prerequisites, all in [docs/building.md](docs/building.md#requirements): clang, lld, llvm-objcopy, squashfs-tools 4.6 or later, ImageMagick, `pip install -r requirements.txt -r test/unit/requirements.txt`, and for a build the stock ZIP `Q2 Firmware V1.36.zip`, SHA-256 `4e298cab6c12d86cfc55565645f7e3ae11d3fb44677a93ca13991e7184ecec4e` (`ZIP_SHA` in `tools/build.py`).

```sh
# Tests that need no stock ZIP and no build. Run these first.
python3 -m pytest test/unit -q                                 # tools/ (about 4.5 minutes, serial)
mkdir -p ~/.cache/q2-pytest
python3 -m pytest test/fw -q --basetemp ~/.cache/q2-pytest/fw  # the payload's C on this machine; needs a PIE python
python3 test/build.py                                          # boot scripts, JPEG checks, dev tags
mypy tools test/unit && mypy test/fw                           # the type check CI runs

# A build (minutes; needs the stock ZIP). --out must be a directory with no update.tar in it.
python3 tools/build.py 'Q2 Firmware V1.36.zip' --out /tmp/q2-dev --dev   # test build, starts q2remote
python3 tools/build.py 'Q2 Firmware V1.36.zip' --out /tmp/q2-build       # release build

# Tests of a build: the real MIPS payload under Unicorn.
python3 test/patch.py /tmp/q2-dev        # the UI payload (about 4.5 minutes, one core)
python3 test/playback.py /tmp/q2-dev     # queue traversal and the wheel's ticks

# The bundled Subsonic app, run for real against a fake server and the firmware's C (no build; Go and ~/repos/q2-subsonic)
python3 test/subsonic_seam.py            # the pinned app; --app DIR for a checkout, --commit SHA (docs/building.md#seam-test)

./tools/format.sh                        # clang-format and prettier, before a pull request; --check changes nothing
```

The full list of suites, with what each needs, is in [docs/building.md](docs/building.md#tests). CI (`.github/workflows/`) runs `test/unit`, `test/fw`, the host suites that need no build, and mypy; nothing that needs the stock ZIP runs there, so run `test/patch.py` yourself after a change to `patch/`.

## Working beside other agents

Many agents share one 16 GB laptop, and a script, not an agent, integrates their work. **If you were spawned as a worker, read [docs/orchestration.md](docs/orchestration.md) first** (the worker's contract: how you register, test, queue your branch and end); if you are the main thread, it is how you run workers, read the queue and stop everything. The short form:

- Register: `q2 agent start NAME --item '...'` in your worktree. Refused means another worker is there: stop and say so.
- Build with `B=$(python3 tools/ci/rebuild.py --dev | tail -1)`: one reused build per worktree, skipped when nothing changed. Not a new `bN` each time.
- Test with `python3 tools/ci/affected.py --run "$B"`, in the foreground: what your branch's changes need. For a payload change that is all of `test/patch.py`, run serially (under five minutes on one core); never `tools/ci/patch_shards.py` on the whole suite, which takes twice as long and seven times the memory ([building: Fast test runs](docs/building.md#fast-test-runs)).
- Wrap anything else heavy in `q2-heavy` (memory, disk, power, no core dump, a deadline). Never `pytest -n auto`.
- Wait with `q2-wait --pid PID --timeout S` or `q2-wait --log FILE --match REGEX --timeout S`. Never a loop around `pgrep`, never a wait with no limit.
- Borrow an emulator: `python3 tools/ci/emu_pool.py get "$B"`, `put SLOT` when done. Don't copy `~/q2-emu-server`; slot 2 is the user's.
- UI work: `python3 tools/ci/q2live.py` rebuilds demo and reloads a pooled emulator on every save under `patch/`, back on your page ([building: Live reload](docs/building.md#live-reload)).
- The trunk (`q2 trunk`) moves only through the merge queue: a commit, merge or push to it is refused. When your branch is done, merge the trunk into it, run `affected.py --run "$B"` again, push, and queue it: `python3 tools/ci/merge_batch.py --mark-ready` (refused if it would conflict: resolve in your branch). Then `q2 agent end NAME --state READY` and end with `READY <branch> <sha>`. Do not wait for the merge; the queue lands it within a batch or sends it back with the failing test.
- A branch for an integration branch (`integ/*`) is not queued: run `affected.py --base <that branch> --run "$B"`, push, end `READY`. The integrator merges with a build after each merge and runs `affected.py --all` and `smoke.py` once, on the last ([orchestration: Integration branches](docs/orchestration.md#integration-branches)).
- Leave nothing running: `q2 agent end` is refused while a job or process of your worktree is alive.

## Traps

- **Never read `docs/internals.md` whole.** It is 832 KB: a paragraph is one line, the longest 10,766 characters. `grep -n '^## '` for the heading, then read that line range, or `grep -o` a symbol with a few hundred characters around it.
- **Shanling's files are never committed.** The stock ZIP, anything unpacked from it and any build output (`*.zip`, `*.tar`, `*.squashfs`, `build/`) stay out of the tree; `.gitignore` covers the usual names, not every path you might choose.
- **`test/fw` refuses a non-PIE python.** The payload's C uses stock's fixed addresses (`0x400000`-`0xc00000`), where a non-PIE python is mapped. Debian's and Ubuntu's `/usr/bin/python3` is non-PIE; `test/fw/conftest.py` stops with a message. Use a python built with `-pie` (`actions/setup-python`'s builds are) and make the venv from it.
- **`--basetemp` needs its parent to exist**, and should be on disk: pytest's default is under `/tmp`, often RAM, and each test loads a 20 MB library.
- **`tools/build.py` fails under `python3 -I`.** It imports its siblings (`from ipod import decode, encode, walk`), and isolated mode drops the script's folder from `sys.path`. `tools/rebase.py` and `docs/rebasing/sitenotes.py` are the opposite: they read untrusted stock files and say to run with `-I`.
- **`tools/format.sh` formats a new `patch/*.c` in either list** unless it is in `UNFORMATTED` (`tools/peq.py`), and needs clang-format 18, the version the tree is formatted with. Without it installed, `CLANG_FORMAT='uvx --quiet --from clang-format==18.1.8 clang-format'`.
- **`tools/build.py` refuses an `--out` that already holds `update.tar`.** Build into a fresh directory, then swap.
- **A build is stale after any edit.** `test/patch.py` and the other `BUILD` suites refuse a build whose `manifest.json` `source_sha256` is not the tree's (`patch/`, `tools/`, `player/`, `ui/`, `assets/`, `docs/manual/`). Rebuild, don't work around it.
- **A new `patch/*.c` is not compiled until it is listed**: in `NAVIGATION` (`tools/build.py`) if it includes `navigation.h`, else in `UI_SOURCES` (`tools/peq.py`). `test/fw` builds from the same two lists.
- **The payload has a hard limit.** Code and constants must fit the 1.5 MB below `SCRATCH` (`tools/build.py`); past it the build fails with `Payload overlaps its scratch page`. Check `patch_bytes` in a build's `manifest.json`. See [architecture](docs/architecture.md).
- **Writable state goes in `.scratch`** (`__attribute__((section(".scratch")))`), zero at start. The link script has no `.data`. That room is 128 KB (`SCRATCH_SIZE`) for every `static` together, and the tighter of the two: a build prints the bytes left (`payload room: ...`, `scratch_free_bytes` in `manifest.json`); a buffer used for one call goes on the stack or the heap.
- **Every stock address is V1.36's.** A new one needs its guard (the expected stock word in `patch_word`, or a prologue check through `HOOKS`), a name in `tools/stock_map.tsv` if Shanling left the function unnamed, and its row in `tools/stock_sites.tsv` ([rebasing](docs/rebasing.md#writing-hooks-that-survive)).
- **A window the wheel should work on must be in `patch/contexts.inc`**, and the build rejects a name that is not a stock window or in `PAYLOAD_WINDOWS`.
- **`ponytail:` in a comment or doc marks a known limit or cost left on purpose**, with what would lift it. Read it before "fixing" the code beside it.
- **Don't change `VERSION`**, and add a plain-words line to [docs/changelog.md](docs/changelog.md) for anything a user would notice ([CONTRIBUTING](CONTRIBUTING.md#changing-the-firmware)).
- **Docs follow the code in the same change**: how a fix works goes in [docs/internals.md](docs/internals.md) and the code's comments, and source comments cite doc anchors (`docs/internals.md#lock-screen`), so renaming a heading breaks them: `test/unit/test_docs.py` fails on each citation that no longer resolves, and on a `file:LINE` in [architecture](docs/architecture.md), which names symbols by file.

## Where code goes

Don't add features to `patch/navigation.c`: give each its own file, as CONTRIBUTING.md's [Where new code goes](CONTRIBUTING.md#where-new-code-goes) says. Add to navigation.c only where the code being changed already lives, and say why.

## graphify

graphify-out/ (git-ignored) is a knowledge graph of the code (god nodes, community structure, cross-file relationships) that exists only in a checkout where someone has generated it with the graphify tool; a new worktree has none, and the tool is not installed on this machine as of 2026-11-22 (`command -v graphify` prints nothing). Without graphify-out/graph.json, skip these rules and search as usual.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:

- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
