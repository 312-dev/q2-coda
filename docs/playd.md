# q2playd

VampOS's playback service ([roadmap: Who owns what](vamp-os.md#who-owns-what)): the server end of the player's socket, the queue and what plays. On today's Vamp `demo` is that server ([player: The socket](player.md#the-socket)); in VampOS `q2playd` is, so `q2player` and `q2ui` play local files with no `demo` ([vamp-os-base](vamp-os-base.md)). This is its first slice: server songs through their app, the cover, and a URL played with audio focus; no resume, play counts, ratings or gapless preload yet ([What is missing](#what-is-missing)).

| What | Where |
| --- | --- |
| Source | `playd/q2playd.c` (one file, one thread, one `poll` loop), `playd/Makefile` |
| In the image | `/usr/bin/q2playd`, the `q2playd` service (`os/package/q2playd`, `/etc/sv/q2playd`) |
| Tests | `test/playd.py` (this machine, a stand-in for `q2player`), `test/os_image.py`'s boot (the real `q2player` under QEMU) |

## What it talks to

| Side | Path | How |
| --- | --- | --- |
| `q2player` | `/tmp/sock_play` | It listens; `q2player` connects, as to `demo`. `{name\argument}` messages ([player: Commands](player.md#commands)) |
| `q2player`'s status push | `/tmp/q2player.push` | A datagram socket it binds: each push makes it ask `player-status` and `media-info`; besides, it asks once a second while a song is loaded, never while none is |
| `q2ui` today | `/tmp/coda-rc.cmdq`, `/tmp/coda-rc.list` | The FIFO and list file `ui/player.c` writes for `demo`'s shim (`patch/coda_rc_cmdq.h`): `q2playd` makes the FIFO and reads it, so `q2ui` needs no change |
| `q2-iap`, the `coda-rc` daemon | `/tmp/coda-rc.ack` | Each FIFO command answered as `demo`'s shim answers it (`coda_rc_shim.c` `cr_ack`): a `<seq> <code>` line for it and the three before it, newest first, the file replaced whole; 0 done, 1 not done, 3 a `jump` to a line that no longer holds its song (the shim's 2 and 9, busy and taken, are not sent: a command here is done or refused at once). The senders wait for their seq there (`coda_rc.c` `ack_poll`) |
| `q2ui` today, `coda-rc`, `q2-iap` | `/tmp/coda-rc.now` | What plays, as `demo`'s shim writes it (`coda_rc_shim.c` `cr_now`; `ui/now.c` reads it): `seq` first, a count that moves with each write (`coda-rc` reads the rest only when it moved, `coda_rc.c` `np_read`), then `title`, `artist`, `album`, `state` (0 stopped, 1 playing, 2 paused), `pos` (ms), `len` (s), `volume`, `id`, and Car Remote's fields: `shuffle` and `repeat` (0 Off, 1 One, 2 All: [The play mode](#the-play-mode)), `hearts` (the song's stars, 0 for none) and `liked` (its like, 0 or 1; the UI pin's shim writes it after `hearts`), each -1 for a source's URL, which cannot be rated ([Ratings and likes](#ratings-and-likes)), `qpos`, `qlen` and `qgen` (the queue file's place, lines and generation), `qlist` (moves with each new queue: a play, a source's start and end) and `path` (the playing file). A `key=value` line each, rewritten whole (a temporary name, then renamed) on a change, twice a second at most |
| `coda-rc` | `/tmp/coda-rc.queue` | The queue for Car Remote's GetQueue, as the shim's `cr_queue` writes it: `gen place lines`, then a line a song in the order it plays (a shuffle's too), its library id, or for a played-as-paths song `0`, its path and two blank names after tabs; past 5,000 songs the 5,000 around the one playing. Written with the now file, and `gen` moved, only when it changes |
| `q2btd`, and clients to come | `/run/vamp/play.sock` | [Q2PLAY/1](#q2play1); `q2btd` sends `output` and, for a headset's keys and its own volume, the transport verbs and `volume` ([btd](btd.md#where-the-music-goes)) |
| `q2pkgd` | `/run/vamp/pkg.sock` | Q2PKG/1's `start <id>`, for a server play of an app not listening ([Server songs](#server-songs)) |
| The library | `/mnt/data/database.db` | Stock's `songtable`: a song's `fileurl`, `name`, `songer`, `album` by its `id`, the id `q2ui` lists |

## Commands

The same verbs from the FIFO (`<seq> <verb>`) and from Q2PLAY/1:

| Verb | What it does | Sends the player |
| --- | --- | --- |
| `play AT SHUFFLE N` | A new queue of N ids (the FIFO's from `/tmp/coda-rc.list`, one a line; Q2PLAY/1's on the next N lines), from the one at AT; with SHUFFLE 1, that song first and the rest in a random order, each once | `set-songurl` (nothing playing) or `set-nexturl` (cutting the song playing) |
| `toggle`, `pause`, `resume` | Pause and play; `resume` with nothing loaded starts the queue's current song again | `mcl-pause`, `mcl-play`, or a song |
| `next`, `previous` | The next or the previous song; `previous` more than 3 s into a song starts it again | `set-nexturl`, or `mcl-seek 0` |
| `seek S` | To S seconds | `mcl-seek` |
| `volume V` | 0 to 100, capped at Max Volume, set on the output ([The volume](#the-volume), [The output](#the-output)) and saved | nothing on the DAC (its own ioctl); on Bluetooth `mcl-setvol` |
| `output dac`, `output bluetooth`, `output bluetooth soft` | Where the music goes ([The output](#the-output)) | `mcl-setoutputway`, `mcl-setvol`, and a song loaded again where it is |
| `stop` | Nothing plays | `mcl-stop` |

The FIFO has `q2ui`'s Play Next and Play Last, `queue next N` and `queue last N` (`ui/player.c` `player_enqueue`; the shim's, `library_pages.c` `queue_apply`), and Q2PLAY/1 the same with the N ids on the lines after it: the list file's N ids put after the song playing in the play order (a shuffle's too) or after the last, the song playing left alone; with nothing queued they are loaded as the queue, not started (a `resume` plays the first); a source's URL and a server list's answer, which keep their own queue, refuse it (1). It also has Car Remote's `jump LINE ID` (`coda_rc.c` `queue_item`, the shim's `cr_jump`): line LINE of the queue file as last written plays if it still holds song ID, the one playing played on (resumed if paused); else answer 3. Car Remote's `mode SHUFFLE REPEAT` sets [the play mode](#the-play-mode), as Q2PLAY/1's `mode` does; Q2PLAY/1's `now` ends with it as the now file's `shuffle=` and `repeat=`. Car Remote's `rate N ID` and the UI pin's `like ID` set the stars and flip the like ([Ratings and likes](#ratings-and-likes)), and `album N ID` makes an album a favourite or not ([Albums' hearts](#albums-hearts)). The shim's other Car Remote verbs, `scan` and `radio`, are refused (1) until `q2playd` has Car Audio's scan and song radio; `find` is [Find My Vamp](#find-my-vamp).

## Gapless

As `demo`'s `mclAutoChange` does ([player: What demo sends](player.md)): with `[PLAYSET] GAPLESS` 1 (read again when `config.ini` changes), a song of 3 s or more that is less than 6 s from its end, by the player's `media-info`, has the next song sent ahead, `{set-gapless\URL|ss=0|-1|P|1|90}` (the cache -1, no hardware type), once; never a `.dsf`, `.dff` or `.iso` on either side. The next is the one the end would take: the same song for Repeat One, the first again for Repeat All unshuffled, none at the end otherwise (a shuffle is drawn again there, and an answer's next not there yet is waited for). The player opens it on its own thread and plays it at the end with nothing between, so that end's `exit` sends nothing: Now Playing moves to the song sent ahead. Any other change of what plays (a play, Next, Previous, a jump, Play Next or Last, the play mode, a source, a stop) first sends `mcl-closegapless`, as stock's queue edits do.

## Mono, Swap and Crossfade

Three words `q2player`'s chain reads as it plays ([internals: Smart Crossfade](internals.md#smart-crossfade), `patch/peq.h`), each an int in a file under `/tmp` that the player maps read-only once it appears (`player/dsp.c` `watch`), so a change is heard at once. `q2playd` writes them as today's `crossfade.c` does: each file is made once, written whole beside and renamed, then changed in place and never replaced, since the player keeps the mapping it took; a file a `q2playd` before left is taken as it is. A file that is not there reads as off, so none is made for a setting that is off.

- **Mono Audio** and **Swap L/R**: `[Q2POD] MONO` and `SWAPLR` (1 on) in `/tmp/q2mono` and `/tmp/q2swap`, read again when `config.ini` changes.
- **Smart Crossfade** (`[Q2POD] XFADE`): `/tmp/q2xfade` holds the next change's fade, 5000 ms with the smart bit (`0x8000`: the player plans the overlap from both songs' loudness and falls back to that plain fade), only with Gapless on and the next song another album's by Cover Flow's album key (a shuffle's every next counts as one), never into a DSD file or one not on the card; else 0. Its high half counts the stops, so no tail the player holds outlives one. `/tmp/q2xfade.next` names the change's two songs, the playing one's path first, a line each, so the player opens the next ahead. It is worked out again only when the queue, its place, the settings or the stops change.

## The play mode

Stock's play mode (`MCL_MODE`), saved as `[PLAYSET] PLAYMODE`: 0 in order, 1 Repeat One, 2 Shuffle, 3 Repeat All; and today's Vamp's two Now Playing controls over it (`np_bar.c`, [internals](internals.md)): `[IPOD] NPSHUFONE` keeps shuffle under Repeat One and `[IPOD] NPREPOFF` says Off was chosen under shuffle. All three are read at the start. Repeat One plays the song again at its own end (Next still moves on); at the queue's end Repeat All, and Shuffle whatever NPREPOFF says (stock's Shuffle never ends), play it again from the first song, a shuffle drawn again; under Shuffle every play is shuffled. `mode SHUFFLE REPEAT` (the FIFO's, Car Remote's SetMode: shuffle 0 or 1, repeat 0 Off, 1 One, 2 All, -1 leaving either; anything else refused) sets them as `np_mode_set` does: Repeat One plays as 1, shuffle with Off or All as 2, All alone as 3, neither as 0, each key written only when it moves; the queue playing is shuffled from the song playing, or given its own order back at it.

Q2PLAY/1 alone has `source` and `focus` ([Sources and audio focus](#sources-and-audio-focus)): a URL needs a holder to tell when it ends, and the FIFO has no answer channel.

A song's `set-songurl` is built as `demo`'s `mclStartPlayer` builds it: the path (a `}` written `%0x7d`), `ss=0` (the second heard, for a song started again on another output), the cache by kind (512 KB, 1024 for `.flac` and `.ape`, 4096 with a 50% fill for `.dff`, `.dsf`, `.iso`), `[PLAYSET] GAPLESS` (0 or 1), the Q2's hardware type 17, and 90. When the player says a song ended (`{player-status\exit}`) the next plays (or, sent ahead, plays on alone: [Gapless](#gapless)); when it did not open (`error`) it is passed over, and after 20 in a row, or an id not in the library 20 times, the queue stops; at the queue's end it sends `mcl-orderstop` and nothing plays. A cut's own close (`player-nextstatus`, `player-stopstatus`) is no end. A player that goes away leaves nothing playing; `runsv` starts it again and `q2playd` takes its connection.

## Ratings and likes

A song has 0 to 5 stars and, apart from them, a like (the heart), as on today's Vamp ([internals: Ratings](internals.md#ratings)). The stars are kept in today's Vamp's table, `/mnt/data/ringnav-ratings`, in its format (`patch/ratings.c`), so a switch either way keeps them: words each holding the song's `listen_key` (the path's FNV-1a and `fnv`'s separator) with its low three bits the stars, 0 a free slot and 7 a rating taken out, placed at the key's hash (`rate_home`) and probed on from there; 4,096 words to start, doubled whenever a new rating would put more than three quarters of the slots in use, up to 16,384 (12,285 ratings), past which a new song's rating is refused and every kept one stays; the last two words the layout mark and the slots in use. It is read at its first use and written whole (a temporary name, synced, renamed) at each change. A file from before the hashing (its ratings from the first slot, 16 KB) is laid out at its first use and kept once as it was, `ringnav-ratings.v1`, as today's Vamp does.

The like is today's Vamp's My Fav, stock's `myfav` table in `/mnt/data/database.db`, so a like survives a switch either way. `q2libd`'s library has no `myfav` ([libd](libd.md)), so `q2playd` keeps the likes in `/mnt/data/vamp/likes.db`'s `myfav` (stock's table's `fileurl` column alone, by path; what `coda-rc --library vampos` lists as Favorites, [carrd](carrd.md#the-library)) and writes each through to stock's `myfav` in stock's form, as today's `catalogue.c` `fav_set_on` does: the song's row out, and for a like its row copied in from `library.db`'s `songtable`, else the card catalogue's `servertable`, the columns stock's `myfav` has (both libraries have stock's columns). A like that cannot be written yet (no `myfav` in `database.db`, or the song's row in a catalogue whose card is away) waits in `likes.db`'s `waiting` and is written within 2 s of becoming possible. At each start the waiting ones are written and the likes are taken again from stock's `myfav`, which today's Vamp may have changed meanwhile, with any still waiting over it; with no stock `myfav`, `likes.db`'s own stand. A song is keyed by its path; a server song playing from its offline copy by its server row's `fileurl` (`catalogue_song_key`), so it keeps one rating however it plays.

The FIFO's `rate N ID` (Car Remote's Rate, the shim's) sets the stars of song ID, 0 taking them out, and `like ID` (the UI pin's shim, `9af5a6f5`, `rate_now_like`) flips its like, the stars left alone. Each answers 0 done, 1 refused (past 5, the table full, a file not written) and 3 when ID is not the song playing or nothing that can be rated plays. The now file's `hearts` and `liked` are the song's.

Each change goes to the servers as today's does ([server-library: Ratings and favorites](server-library.md#ratings-and-favorites), `catalogue.c` `rated_line`): a line `<listen_key>\t<sid>\t<stars=N|like=0|1>\t<unix time>` appended to the `ratings.out` of every app on the card whose `q2app` says `ratings=2` (a `ratings=1` app is sent nothing), the sid the song's server row's (`servermeta`), or for a card song the one its duplicate names (`serverdup`), in that row's app's line alone.

The servers' own come in from each `ratings=1` or `ratings=2` app's `ratings.in` (written whole by the app, in `ratings.out`'s columns), looked for every 2 s: `stars=N` is kept by the line's key, `like=0|1` is the song's path's (a server row's by its sid, a card song's by its key in the library), a server row's offline copy taken out of the likes either way, written through as any like; a `ratings=1` app's one number is its star at five (the like, the stars left alone), else that many stars and no like. A line is passed over when the song's own `ratings.out` line of the same kind is newer (one number counts as both), and the file is removed once read; one naming a sid waits while the card's catalogue is not there. The caps line an API 0 app is given has `ratings` and `likes` ([packages](platform/packages.md)).

### Albums' hearts

An album has its own 0 to 5 hearts, as on today's Vamp ([internals: Ratings](internals.md#ratings), "Albums"), in `/mnt/data/ringnav-album-ratings`, the song table's format, keyed by Cover Flow's `album_id` (`coverflow.c` `album_ident`): an FNV-1a hash of the album name and album artist with ASCII case aside, else of the name and the album's folder (disc folders such as `CD2` or `Disc 1` as their album's, case kept). The FIFO's `album N ID` makes song ID's album (a card song's or a server row's) a favourite at 5 or not at 0, the queue menu's Favorite and Unfavorite; there is no Rate Album, so any other N is refused (1), and 1 to 4 hearts kept before stay as they are. An album's favourite is its songs' like: reaching 5 likes every song with the album's key in `library.db`'s `songtable` and the card catalogue's `servertable`, leaving 5 takes each out of the likes, written through to stock's `myfav` and told to the servers as any like, their stars left alone. As today, leaving 5 takes out a song liked on its own too, since nothing records which were. It answers 3 when ID is no song of the library.

### The card's copy

`/mnt/data` is not on the part of the Q2 that USB storage shows, so the card keeps today's Vamp's plain copy for a computer, `/mnt/mmc/.ratings.tsv` (`patch/ratings.c`, [internals: Ratings](internals.md#ratings), "Card copy"), output only. Two comment lines name the columns; then tab-separated `song`, stars, liked (1 for a like), path and a CUE track's start (always empty: `q2playd` has no CUE tracks); and `album`, hearts, name, album artist and, for an album without a name or an album artist, its folder. Tabs and line ends in a field are written as spaces. The tables hold only hashes, so a pass reads the names back: a line for the Unknown Album card's hearts (a table today's Vamp wrote may hold one), then the likes (liked, with any stars kept for them), then `library.db`'s `songtable` in id order, then the card catalogue's `servertable` (a server song's stars are kept under its row's `fileurl`), a song's line and, at the first row of its album, the album's; a page of 256 rows each time round the loop, the ratings still to find sorted for a binary search, a table read on only while some are. A rating whose song or album is in none of them (deleted from the card, or its server signed out) has only its hash and stays out until it is back. The whole file is built in memory and written only if it differs (a temporary name, synced, renamed), so a pass after the start normally leaves the card alone; once the new one is written, a file with more lines is renamed `.ratings.tsv.1`, unless that has more still, so a lost table or a half-built library cannot take the only copy. A pass starts 5 s after a change of the stars, a like or an album's hearts (from the FIFO or a server's `ratings.in`), 5 s after `q2playd` starts, when the card comes back (its line in `/proc/mounts`) and when `library.db` or the catalogue changes (a scan); with the card away it waits for the card. A read that fails leaves the copy as it was until the next change.

## Play counts

Today's Vamp's ([internals: Play counts](internals.md#play-counts)), in its file. `q2playd` follows the player's second (each `media-info` answer): a step of 1 to 3 s while the song plays is heard, a longer one is a seek and a pause hears nothing. A song longer than 30 s counts once half of it, or 4 minutes, has been heard, once a play; another song, or the second falling back under 2 s from past 30 s (Repeat One, a seek to the start), starts a new play. The counts are 512 key/count pairs, 4 KB, in the card's `.q2pod/ringnav-plays`, read at the first count and written whole (a temporary name, synced, renamed): the song counted moves first, and with no free slot the furthest back of the lowest counts, the least recently played, is replaced. A song is keyed as its [rating](#ratings-and-likes) is. Songs under the card's `Podcasts` or `Audiobooks` and `.m4b` files are not counted, as today. With no card copy yet the flash file of a release before, `/mnt/data/ringnav-plays`, is read and copied to the card once, never written (`card_store.c`'s blob); with the card away (no `/mnt/mmc` line in `/proc/mounts`) the counts are kept in memory and written within 2 s of its return. Most Played is the UI's to list.

## Resume

Today's Vamp's places for long songs ([internals: Resume](internals.md#resume)), in its file. A song at least **Resume Songs** long (`[Q2POD] RESUMEMIN`, minutes: 20 to 120 in fives, 30 by default, 0 Off), or spoken (an `.m4b`, or under the card's `Podcasts` or `Audiobooks`) whatever its length, keeps its place by its path's hash in 512 key/second pairs, 4 KB, the card's `.q2pod/ringnav-resume`, the most recent first, written whole: each 60 s of movement, once the second stands still two reads (a pause) and as another song starts. A place within 30 s of either end is forgotten. A long song with a place that starts playing under 5 s in seeks there; started paused, it waits for Play. A song's first second read only notes it, so the song before's time never counts for it, and a place is counted from where the song was first read. The flash file of a release before (`/mnt/data/ringnav-resume`) is read until the card has one, and with the card away the ring is kept for it, as the [play counts](#play-counts) are. Not here: today's restart guard ("Press again to restart" before Previous or a pick restarts a song with a place, the UI's) and CUE books' chapter places (`q2playd` plays no CUE tracks).

## Memory Playback

Today's Vamp's queue snapshot ([internals: Memory Playback and a streamed queue](internals.md#memory-playback-and-a-streamed-queue), `playback.c` `playback_save`), in its format, so either system brings back what the other kept. While `[PLAYSET] MEMORYPLAY` is 1 (Track) or 2 (Location), or `[SYSSET] CARMODE` is 1 (read again when `config.ini` changes), a queue of library songs, or an app's answer ([Server songs](#server-songs)), is kept in the card's `.q2pod/ringnav-queue` as version 4, today's for a queue without advanced play: the header (magic, version, size, checksum, songs, place, second, shuffle 0, repeat 2, folder 0, cursor the place, no history, no Play Next list, type `0xf001`), the queue's order twice and as many zeros, then each song's length with its NUL, CUE start and end (0) and path (a server song's `fileurl`; an answer's songs by their card paths, the Stream Cache copies there so far), in play order; the checksum is FNV-1a over the whole with its own word 0. It is written again when the queue or its place changes, and the second goes beside it in `ringnav-queue-elapsed` (its checksum, the snapshot's, the place, the second) at a pause or a stop, every 30 s playing and at `q2playd`'s end. A source's URL is not kept (the kept queue stays as it was), and a queue past 999 songs drops the kept one, as today. At the start the kept queue comes back paused with nothing loaded: Location at its second, Track from the song's start; in car mode it plays at its second once the player connects (stock's `memeory_startplayer`, `ringnav_boot`). The checkpoint's second counts only for the snapshot it names, at its place. A snapshot with advanced play (version 3, or 2) comes back as its queue's rows, its own order not `q2playd`'s; a song no longer in the library is left out (the place then the next song kept); a damaged one brings nothing back. A snapshot holding a Stream Cache copy (an answer's) comes back as the paths whose files are there, as it played, and its songs not on the card are asked of their app ([A streamed queue at a restore](#a-streamed-queue-at-a-restore)). With no card copy the flash files of a release before (`/mnt/data/ringnav-queue` and its `-elapsed`) are read; with the card away nothing is written until it is back.

### A streamed queue at a restore

An app's answer plays from the songs' downloads, and the snapshot holds only those on the card, so the rest are kept beside it as today's Vamp keeps them (`playback.c` `save_tail`, [internals: Memory Playback and a streamed queue](internals.md#memory-playback-and-a-streamed-queue)): `.q2pod/ringnav-queue-stream`, its magic (`0x51325254`), an FNV-1a checksum of what follows, the snapshot's checksum, a count, then the paths of the m3u's songs from the one waited for on (card paths, as the answer's songs are taken), each with its NUL, at most 999 with the queue; with none the file goes. It is written with each snapshot, so a song landing or the app's rewrite of its lines writes both. A tail naming another snapshot's checksum is passed over.

At the start, a snapshot that comes back as a stream's paths asks the app whose folder holds a saved song (`/mnt/mmc/.<id>/`) for the rest, as `addon_resume_ask` does, when its `q2app` says `resume=1` and a song after the current one was not restored (a file gone, or a tail's song): once the app listens (started through `q2pkgd` as for a catplay) `/tmp/q2-<id>.resume` is written whole (beside and renamed), `<seq> <index> <seconds> paused|playing` (`playing` in car mode) and then every saved song's path a line, the snapshot's then the tail's, the index the current song's among them. The app answers `resumeack=<seq> <code>` in its state file (0 resumed, 1 not its songs, 2 it cannot) and a `.play` of that seq whose m3u starts with the song restored (the same path, or the same app and sid by a Stream Cache name or a server row's): that song stays at its place as it is (paused stays paused at its second, nothing loaded; one playing in car mode plays on), the restored songs before it leave the queue, and the m3u's songs after its first are the queue's rest, read as any answer grows. The app not listening within 30 s of the restore, no `.play` within 30 s of the request, a code other than 0, an answer starting with another song or another queue played first: the restored songs on the card are the queue, and the log says why. Today's Up Next lists the saved songs still to come meanwhile; here the queue file lists only the songs on the card ([What is missing](#what-is-missing)).

## Find My Vamp

Car Remote's Find reaches the FIFO as the shim's `find` and `find stop` (`coda_rc_shim.c`); the jingle is `q2sysd`'s ([sysd: Find My Vamp](sysd.md#find-my-vamp)), asked over Q2SYS/1: answered 0 once it plays and 2 (`UNAVAILABLE`) when `q2sysd` refuses it (no buzzer driver) or is not there. While `q2sysd`'s mark `/run/vamp/finding` is there the now file ends with `find=1`, which coda-rc sends as `NowPlaying.finding`.

## Key Tone

The Clicker's click in the headphones is `q2player`'s ([player](player.md), `mcl-click`): Q2PLAY/1 `click wheel`, `click button` or `click beep` sends `{mcl-click\KIND}` to the player, which mixes it into the song playing or plays it in silence of its own, while the queue's player owns the output; with a source holding the player, or no player, it answers `err click`, as `clicker.c` sends nothing while another source owns the output. The route (Key Tone, the Clicker's choice, what listens) is [q2gate](gate.md#key-tone)'s.

## The EQ switch

Control Center's EQ circle, as `peq_ui.c` `eq_toggle` and `eq_commit` turn it (docs/internals.md#3eq): Q2PLAY/1 `eq on` plays the parametric EQ when none plays and leaves an EQ already playing (the 3EQ or the PEQ) as it is; `eq off` plays none. Either way the state is `demo`'s own, `/mnt/data/peq-active` (`patch/peq.c` `eq_load_from` and `eq_save_to`, linked into `q2playd` with `patch/hash.c` and `patch/peq_level.c`), saved with the page's hold cleared and PEQ's Auto preamp as the cut for every standard rate (`peq_level.c` `eq_auto_level`, the editor's definition, so a state saved here plays at the level the editor would have saved). A change writes `[PLAYSET] EQFLAG` (today's Vamp puts the filter into the chain at boot only when it is set) and sends `q2player` stock's `{mcl-seteq\...|1}`, on which it reads the state again and ramps to it (`player/dsp.c` `dsp_eq_changed`); a state that cannot be saved is `err` and changes nothing. `eq` answers whether one plays and which. At the start, as `peq_ui.c` `peq_boot`, a hold left by a page goes and an Auto saved by another version is made the cut for every rate. The EQ page itself (bands, presets, EQ per Output) is `q2ui`'s to build; [q2gate](gate.md) carries the circle's `set eq` and the `eq` slot.

## Q2PLAY/1

The socket the UI is meant to move to, `/run/vamp/play.sock`. Its protocol is Vamp API 1's playback page, [Q2PLAY/1](platform/playback.md), with its commands, its `now` fields and their encoding, its capability words and the transcripts its conformance test replays here. `ui/player.c` and `ui/now.c` say they are what changes when `q2ui` stops going through `demo`'s queue; with this socket `player_send` becomes one line written and its `ok` read, and `now_read` the `now` lines a `watch` delivers, with no inotify on `/tmp`. The now file for `q2ui` keeps the shim's format, a field a line and no encoding, with any line end or other control byte in a value made a space, and its `pos` in milliseconds; Q2PLAY/1's `pos` is whole seconds.

Its rating words, `rating`, `rate`, `like` and `album` ([Q2PLAY/1: Ratings](platform/playback.md#ratings)), name any song of the library by its id (0 the song playing), where the FIFO's `rate` and `like` name only the song playing; they keep and tell the stars, likes and albums' hearts as the FIFO's do ([Ratings and likes](#ratings-and-likes)), and `like` sets the like rather than flips it.

Only root and a package whose user is in the `playback` group get past the hello; anyone else is answered `err permission` and logged ([Packages: Users and groups](platform/packages.md#users-and-groups), `test/perm.py`). The socket is mode 0660 and that group's.

## Sources and audio focus

A `source URL` from a Q2PLAY/1 client (a DLNA renderer, an app's stream) plays one `http://` or `https://` URL in place of the queue, which is put aside whole: its ids and play order, or an app's m3u, its place, its position and length, and whether it was playing. The URL goes to the player as a song does (`send_song`: `ss=0`, the cache by the URL's last dot, a `}` as `%0x7d`), as a cut (`set-nexturl`) when something is loaded; `q2player` opens it through MPlayer's stream layer ([player: Streams](player.md#streams)). A decoded URL holding a space, a control byte or `|` (the player's field separator) is refused, as is any other scheme: a local path would let a package play a file its permissions do not reach once they are enforced. The cover file is removed.

The client is the source's holder until it gives it back (`focus release`), its connection closes, or the player is taken from it; the protocol's page lists when it is told and what comes back ([Q2PLAY/1: Audio focus](platform/playback.md#audio-focus)). A queue given back is **paused and not loaded**: `now` shows its song, position and length, the cover is its song's again, and `resume` (or `toggle`) sends that song with `ss=` its position in whole seconds. A pending catplay is cancelled by a source.

Decisions: the queue comes back paused rather than playing, so a phone that stops casting does not start the Library's music on its own (Android resumes after a short loss; a cast is no short loss); and a `play` drops the queue put aside, because the user chose new music.

## AirPlay

The AirPlay sender is the q2-airplay app ([internals: AirPlay sender](internals.md#airplay-sender)): it makes `/tmp/q2cast` (`cast_tap`, `patch/peq.h`) and beats it, and `q2player`'s DSP chain (`player/dsp.c`, the same code today's Vamp ships) writes what plays into its ring and keeps the Q2's own output silent while the tap's `volume` is 0 or more. On today's Vamp `demo` writes the host's half (`patch/airplay.c`); in VampOS `q2playd` does, with the same layout (mirrored in `q2playd.c` as the app mirrors it):

- It looks for the file once a second until it is there (its magic and size read before it is mapped), then every 250 ms writes the player's `status` (1 stopped, 2 playing, 3 paused), Max Volume and `volume` (the speaker's level while one plays, else -1, so the Q2 is heard) and bumps `beat`.
- While the app beats (its `want` under 1.5 s old), the playing song's `path`, `title`, `artist`, `album` and `length` go to `/tmp/q2cast.track` once a song (written beside and renamed, `track` bumped), again when its length becomes known.
- When the app's state becomes `CAST_ON` the volume is the speaker's: the earphones' level and Max Volume kept (the level saved as `PLAYSET VOLUME`), the limit lifted, and the level taken from the app's `spk` (a new `spk_seq`, a reconnect, is taken again) or else `[Q2POD] AIRVOL` (35 when unset). While it plays a `volume V` changes the speaker's level only, saved as `AIRVOL`; the DAC is not set. When it stops, or its beat goes stale, the speaker's level is saved as `AIRVOL` and the earphones' comes back, set on the DAC and saved.

The app runs as a service package (`/etc/sv/q2-airplay`): once added (`q2pkgd app-add /mnt/mmc/.airplay`, its manifest `kind=service`, `permissions=playback,network-hold,background`, [Packages: Examples](platform/packages.md#examples)) `q2pkgd app-run` starts it as its own user; until then the service waits and looks again every minute. Not yet: the lyrics following the speaker's place (`airplay_lyrics`, `q2ui`'s), the ⋯ row that opens its page (`q2ui`'s), Bluetooth's output key on the way back (VampOS has no Bluetooth yet), and the app's own release with an API 1 manifest (`group-a-study/q2-airplay`).

## The volume

**What stock does** (learned from `demo`'s code, privately, and written here as the interface; [study hygiene](vamp-os.md#study-hygiene)): `device_set_volume(v, save)` is the one place the volume is applied. On the Q2's own DAC it calls `mclSetLocalVol(L, R)`, which is one `ioctl(/dev/shanling_dac, 0xc0044d00, &x)` with `x = (L & 0xff) << 8 | (R & 0xff)`, done only once the DAC is open. `L` and `R` are on the same 0 to 100 scale as the volume itself, both `v`: the mapping from 100 steps to the CS43131s' attenuation is the driver's (`codec_cs43131.ko`), not `demo`'s. Its other cases:

| When | Left, right |
| --- | --- |
| The usual case: the DAC | `v`, `v`; and `mclSetBtVol(v, v)` too, which sends `{mcl-setvol\v<<8 \| v}` only while the output is Bluetooth |
| Line out fixed (`g_output_way` 1 with the DAC as the way) | 100, 100, whatever `v` |
| A USB DAC (way 2) | `mclUsbAudioSetVol`, `v`, or 100 with USB volume fixed (`g_usbvol_mode` 0) |
| Bluetooth receiving, or AirPlay received | `v` scaled by the sender's level (over 127 or over 100) |

Balance is not here: it is a separate ioctl (`config_balance`).

**What q2playd does**: the usual case. At its start it reads `[PLAYSET]` in `/mnt/data/config.ini`, stock's file: `VOLUME`, or `BOOTVOLUME` when `BOOTVOLFLAG` is set (Default Volume), capped at `MAXVOLUME` (Max Volume, 100 when absent), and sets the DAC; each `volume V` (refused outside 0 to 100, held to Max Volume) is set on the DAC at once and written back as `VOLUME` 2 s after the last change, the file rewritten whole with that one line changed, so stock and today's Vamp read it as before. It keeps `/dev/shanling_dac` open beside `q2player`, which uses it for the mode and the mute. With no `/dev/shanling_dac` (the emulator) the volume is kept and shown and the boot log says so once.

Decision: the volume is set by `q2playd`, which owns its level, rather than by `q2sysd` as the roadmap's table has it ([Who owns what](vamp-os.md#who-owns-what)): stock does it in its player module (`mcl`), it is one ioctl, and splitting it across two processes would make every wheel tick a message. The DAC's power and its gain and filter stay `q2sysd`'s.

**Needs a Q2**: the driver's law, 0 to 100 into decibels (measured with a level meter at the jack, or read from the driver's register writes over I2C with `i2cget`); whether the ioctl does anything before the DAC is powered and in PCM mode with no `demo` to do that; and the line-out and USB cases above, which are not built; Bluetooth's is [The output](#the-output).

## The DAC's output

As stock's `config_outputchannel(g_headset_output, 2)`, which `player_start`, `player_play_pause`, `player_change_music` and a paused seek call before the player plays: on the DAC, before each song is sent, before a `resume` and before a source's URL, `q2playd` sets the headset mode for the jack in use (`mclSetHeadsetMode`, ioctl `0xc0044d1c` on `/dev/shanling_dac`: 1 for the 4.4 mm jack when it is plugged, else 0 for the 3.5 mm, `check_outputdevice`'s choice) and powers the DAC (`mclSetDacPwr`, ioctl `0xc0044d1a` with 1, the Q2's case of it), every time, as stock does. A plug or an unplug of the 4.4 mm jack while a song plays does the same (`config_bal_output`, `config_po_output`). After 30 s with nothing playing the DAC is powered off (`check_dacoff_state`, a count each second to 31), and so it is at a move to Bluetooth (`config_outputchannel`'s Bluetooth). The jacks are `q2sysd`'s ([sysd: The jacks](sysd.md#the-jacks)), read from `/run/vamp/jack` (`po=N bal=N`), which it writes at each change.

## The output

Where the music goes, as `q2btd` says it ([btd: Where the music goes](btd.md#where-the-music-goes)): `output dac` (the start), `output bluetooth` (a headset with absolute volume: the player at unity, the level the headset's, which `q2btd` writes) or `output bluetooth soft` (a speaker or a car: the player's own gain at the level). At a change `q2playd` sends `q2player` `{mcl-setoutputway\0}` or `{mcl-setoutputway\1}` and the level, as stock's `mclSetBtVol` does: `{mcl-setvol\L<<8|R}` with the level on both on `soft`, 100 on both (unity, the volume filter out, [player: Output](player.md#output)) otherwise. `q2player` takes a new way only at its next song, so a song loaded is started again where it is heard, as demo's restart after an output change does: `mcl-stop`, then `set-songurl` with `ss=` the second heard, then `mcl-pause` if it was paused. A `q2player` that connects again while the output is Bluetooth is told the way again.

**A level each.** As on today's Vamp, Bluetooth keeps its own volume, `[PLAYSET] BT_VOLUME`, beside `VOLUME`, the DAC's: at a change the departing level is saved (at once, if a change waits for its 2 s) and the incoming one taken, capped at Max Volume, and a Bluetooth level never saved is the DAC's. On Bluetooth the DAC's ioctl is not sent.

`test/playd.py` `test_the_output_moves_the_song_where_it_is_and_keeps_a_level_each`: the messages and their order at each change, the song started at 42 s and paused when it was, unity and the soft level, the two keys in the file, nothing sent for the output already in use. Five broken copies (no restart, one key for both, no unity, the pause lost, the DAC set on Bluetooth) each fail it (`Q2PLAYD_SOURCE`).

## Server songs

A play whose list holds server rows (ids from `0x40000000`, which `q2libd` writes into the card's `/mnt/mmc/.vamp/catalogue.db` `servertable`, [libd](libd.md)) is the app's to fetch, as on today's Vamp ([server-library: Play request](server-library.md)). `q2playd` keeps the firmware's side of that contract:

1. The app is the one whose catalogue the row is (`/mnt/mmc/.<id>/cat/...`). Without its `/tmp/q2-<id>.browse.sock` (none since boot, or gone after its own idle exit), `q2playd` asks `q2pkgd` to start it (Q2PKG/1 `start <id>`, [Packages: Starting and stopping](platform/packages.md#starting-and-stopping-q2pkg1); a blocking exchange of at most 3 s) and waits up to 15 s for the socket, polling it every 200 ms. With the socket there, the list goes to it as `/tmp/q2-<id>.catplay`, written beside and renamed: `<seq> <start>`, then a line per row in play order (a server row's `fileurl`, a card song's path), `<start>` the chosen song's line (0 when shuffled, the list already in shuffle order).
2. Nothing plays until the answer: `/tmp/q2-<id>.play` changing to `<seq> <m3u>` with that catplay's seq. Its m3u's card paths (Stream Cache copies for server songs, from `<start>` on) are then the queue, played as paths, the file's name as the title, each waited for until it is there ([The answer as it grows](#the-answer-as-it-grows)).
3. No answer within 4 s of the catplay, an answer to another seq, `q2pkgd` not starting the app (no `q2pkgd`, or its `err`), or no socket within 15 s of the start: the list is played offline ([Offline copies](#offline-copies)). The catplay is written only once the socket is there, as today's Vamp does: an app takes a `.catplay` present at its start as one already answered.

Not yet: Now Playing while the answer is awaited, and the `.stream` file's loading state (`q2ui`'s to show, [Download Ahead](#download-ahead)).

### The answer as it grows

An app answers with its m3u at once and fetches the songs after the first while they play, so a line may name a file not there yet (without `grow` the app renames each download into place when it is whole; with it, [below](#a-song-played-while-it-arrives), it writes the song in place as it arrives). `q2playd` reads the m3u as the firmware's `m3u_songs` does (`patch/addon.c`): its entries in order, a BOM, `#` lines and blank lines skipped, an entry off the card (not `/mnt/mmc/...`, or with a `..` segment) passed over, up to the first whose file is not there yet (or, arriving, has not its start yet). It reads the file again when it changes (its size and time, looked at every 200 ms) and when the song waited for lands. Entries are counted, so the app may rewrite the lines after those taken (the one waited for, say).

A song's end with the next not there yet is no end of the queue: nothing is sent, the state stays playing and Now Playing shows the song waited for (its server row's title, artist and album when `servermeta` or the Stream Cache name says which), and it plays as it lands. A `next` then stops the song playing and waits the same, as the firmware's Next does (`addon_next_waits`); a `next` while waiting changes nothing. An answer whose first song is not there yet plays nothing until it is. Paused while it waits, the song lands paused and `resume` plays it. A new play, or a source, ends the wait (a source's queue given back waits again).

### A song played while it arrives

The caps line has `grow` (`q2player` plays a file still arriving, `player/grow.c`), so the app writes a song in place as it arrives and says how far it has come in `/tmp/q2-<id>.stream` ([server-library: Starting before the end](server-library.md)): `#Q2STREAM/1`, then `<state> <bytes> <total> <length ms> <path>` a song, tab-separated. A line of the answer whose file is there is queued once its `.stream` line is `done` or `fail`, or `get` or `stall` with `START` bytes there: 3 s of the song (total x 3000 / length), at least 256 KB, or the whole file when the total or the length is unknown; `wait` waits. A `.stream` not written for 3 s is stale (the app died or stopped) and its `get` lines read as `fail`. A song with no line is whole. Until then it is waited for as a missing file is ([The answer as it grows](#the-answer-as-it-grows)); the file is read again when it changes. At the bytes there are, the player waits rather than end, and writes `/tmp/q2player.wait` meanwhile, which is the UI's to show.

### Offline copies

When `q2playd` plays a server list itself it keeps the firmware's `cat_offline` rule (`patch/catalogue.c`): the list's card songs, and its server songs that have an offline copy (`catalogue.db`'s `servermeta.local`, which `q2libd` keeps from the catalogue and `catalogue.avail`, [libd: Offline copies](libd.md#offline-copies)), in the list's order, from the first of them at or after the chosen song (the first of them when none is after it). A server song plays from its copy's path under its own id, title, artist and album, and shows its row's cover (`covers/<album id>.jpg`, by the album id in its `fileurl`). One with no copy is passed over.

An app whose `/tmp/q2-<id>.state` has the line `server=down` is handed nothing: its list is played offline at once, as the firmware does for an app whose server is gone. A play whose chosen song is that app's server song with no copy is refused (`err play` on Q2PLAY/1; the firmware's "Not available offline"), and what was playing goes on.

An app's m3u may name a copy anywhere on the card: a song played as a path takes its server row's title, artist, album and cover when `servermeta.local` names it, as well as for a Stream Cache path with its sid in the name.

### Wi-Fi's state

Before a server list goes to its app, `q2playd` asks `q2netd` (Q2NET/1 `status`, [network](platform/network.md)), as the firmware asks `networkGetConnectStatus` and Smart Wi-Fi (`cat_online`, `smart_wifi_wait`): joined (`state=connected`), the list goes on as above; Wi-Fi off by the user (`state=off smart=0`), or on and joined to nothing (`searching`, `scanning`, `associated`), it is played offline at once; Smart Wi-Fi's radio off (`state=off smart=1`), `q2playd` sends `wake`, asks `status` every 500 ms, and hands the list over once it is joined, or plays it offline when no link comes within 15 s (the firmware's `SMART_CONNECT_MS`). With no `q2netd` to ask (no socket, or no answer within 1 s) the list goes on as above.

## Download Ahead

Streaming > Configuration's **Download Ahead**, `[Q2POD] AHEAD` in `config.ini` (0 Off, 1, 2 or 3 songs; missing or anything else 2, as the firmware's `ahead_n` reads it), is told to the app in `/tmp/q2-<id>.ahead` as the firmware does ([server-library: Download Ahead](server-library.md#download-ahead-and-the-streaming-state), `patch/stream_state.c`): `#Q2AHEAD/1`, a tab, `seq=` the `.play`'s seq, a tab, `n=`, then one card path a line. It is written just before each `.catplay`, for that catplay's seq, with `n` and no songs (the queue holds none of the list yet, so the app never runs the list on its own default), and then while the queue playing is that app's answer: the songs the queue holds after the one playing, at most `n`, in queue order (the catplay's order, shuffle already in it). It is rewritten when they change (a song's end, a `next` or `previous`, a song landing and so queued) and when the setting changes (`config.ini` looked at with the m3u, every 200 ms); never for the position or a pause, and never twice the same. Written beside and renamed. `q2pkgd` puts `ahead` in an API 0 app's caps line ([Packages](platform/packages.md#examples)).

The word also tells the app the firmware reads `/tmp/q2-<id>.stream`, how far each planned song has come. `q2playd` reads it for `grow` ([A song played while it arrives](#a-song-played-while-it-arrives)); its other use is Now Playing's loading row (the spinner and `<bytes> of <total> MB`, `patch/np_stream.c`), which is `q2ui`'s to read and draw.

## The cover

At each song's start its cover is copied to `/tmp/externpic.jpg`, where stock's cover thread leaves it and `q2ui` reads it (`ui/now.c`), written beside and renamed; with none the file is removed, so the last song's does not stay. A card song's is `q2libd`'s (`library.db`'s `vamp_cover`, [libd: Covers](libd.md#covers)); a server row's its app's `covers/<album id>.jpg` ([server-library: Covers](server-library.md)). A song of an app's m3u takes its row's title, artist, album and cover: the card song of that path, or for a Stream Cache copy (`/mnt/mmc/.<id>/stream/.../<title> [<sid>].<suffix>`, `patch/stream_path.h`) the server row of that sid.
