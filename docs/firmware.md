# Firmware and versions

Every piece of firmware and software on a Q2 running Vamp that someone else wrote: the version on the device, the newest public one, the gap, and whether Vamp can update it. The libraries Vamp rebuilds from source are in [third-party](third-party.md), which says how; this page lists them for the whole picture and covers what that page does not: the chips' own firmware, the vendor's drivers and the binaries Shanling ships. The hardware they run on is in [hardware](hardware.md).

Versions on the device were read from stock V1.36's files (its kernel image, the rootfs of a Vamp build, which keeps them byte for byte) and from a Q2 on 2026-11-25; the newest public versions were checked on 2026-11-25. Recheck those before acting on a gap.

## Bluetooth controller

`/firmware/rtlbt/rtl8733bs_fw` is loaded into the RTL8733BS's RAM by `rtk_hciattach` at every boot; nothing is flashed in the radio, so a different file is undone by the next `update.tar` or by putting stock's back. Stock's file against the newest public Linux build of the same chip:

|              | Stock V1.36                                      | Realtek Linux package, 2023-08-01                                                                                                                                |
| ------------ | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Size         | 57,020 bytes                                     | 55,580 bytes                                                                                                                                                     |
| Format       | epatch v1, signature `Realtech`                  | the same                                                                                                                                                         |
| Version word | `0xd5c81143`                                     | `0xdcc76fec`                                                                                                                                                     |
| Coex tag     |                                                  | `BTCOEX_20230616-0e0e`                                                                                                                                           |
| Patches      | 2, for chip IDs 1 and 3: 12,337 and 44,469 bytes | 2, for the same chip IDs: the chip ID 1 patch byte-identical to stock's; the chip ID 3 patch 43,029 bytes, 91% of it the same bytes as stock's in five long runs |
| Project ID   | 19                                               | 19                                                                                                                                                               |
| Config       | baud word `0x04928001` (3 Mbaud)                 | identical but the baud word, `0x04928002` (1.5 Mbaud)                                                                                                            |

The package's release note renames the chip from RTL8723F to RTL8733B. Mainline Linux's `btrtl.c` has no entry for project ID 19, and linux-firmware has no 8733 or 8723F file. A third build, `0xdda9b625` (46,156 bytes), is an Android vendor build found by a ROCKNIX port. Realtek's version words are not dates, so which build is newest is unknown; Shanling's Wi-Fi driver (2025-05-21) and `rtk_hciattach` (2023-09-21) are newer than the package, so stock's controller firmware is probably not older than it (inferred, low confidence).

**Coex compatibility.** The Wi-Fi driver's coex reads `BT_Dez 0x0c`, `BT_Rpt 0x0e (Match)`: the controller firmware reports coex version 0x0e and the driver needs at least 0x0c. `B_FW 0x10c81143` (the low 24 bits of the version word) is shown, not compared. The 2023 package's tag ends in `0e0e`, which reads as coex version 0x0e too (inferred, medium), so it would most likely still match; the coex code and parameter table are the Wi-Fi driver's and do not change with the Bluetooth file.

**Not swapped**, for these reasons, none of them coex:

- Nothing ties the dropouts or the UART storms to the controller firmware: no storm on record came mid-stream, and the audible stalls have outside causes ([bluetooth](bluetooth.md#the-dropouts-of-2026-11-24)).
- The version words do not order the builds, so the public one may be older.
- Stock's build is the larger, and probably not older.

A trial would be worth it only if a storm's H5 debug lines show the controller resetting (its sequence numbers starting again) rather than bytes damaged on the wire. If one is run, on a dev build: read `cat /proc/net/rtl8733bs/wlan0/btcoex` at once and check `BT_Rpt` still says Match, and `hciconfig hci0 version` for the new revision. A file that fails to load gives **Bluetooth abnormal**, which Vamp stops at the Bluetooth Stopped page rather than a reboot loop.

## Touch controllers

Both Hynitron drivers carry firmware images for the chips they drive; what they do with them differs:

- **`hyn_touch` (the touchscreen) updates the chip at boot.** Its probe queues an upgrade work when `need_update` is set, and `cst8xxT_init` sets it when the bundled image's checksum differs from the chip's and the image's version is not lower than the chip's. The bundled image (in `.data`, 15,366 bytes) is IC type `0xb6`, project `0x02603138`, version 2, checksum `0xb925`. The chip reports `fw_version:0x02,chip_type:0xB6,checksum:0xB925,project_id:0038` (`/sys/hynitron_debug/hyntpfwver`, read on a Q2 on 2026-11-25): an exact match, so no update runs. A different `hyn_touch.ko` with another image would flash the chip at the next boot.
- **`hyn_slider` (the wheel) never updates the chip.** Its bundled image is IC type `0xb6`, project `0x02302111`, version 1, checksum `0x56dc`, but nothing in the module schedules its upgrade path (no `queue_work_on` anywhere in it). It defines a `hyntpfwver` attribute under a `hynitron` kobject, but on a Q2 only `/sys/hynitron_debug` exists, and that is the touchscreen's, so the wheel's chip version is not readable through the driver.
- Both modules also carry CST66xx images (`fw_module1`, `fw_module2`, 40,964 bytes; IC types `0xcaca220e` and `0xcaca220c`) for other Hynitron parts; the clients' name `hyn,66xx` comes from the same shared driver code, not from the Q2's chips.

The images can be pulled out of the modules for comparison with the study's scripts' method: the `hyn_6xx_fw` and `fw_module*` symbols and the `cst8xxT` image's offsets (`.data+0x180` in `hyn_touch.ko`, `.rodata+0x2aca8` in `hyn_slider.ko`); the header holds the IC type, project, version and checksum.

## Unknowns

- **The touch wheel's chip firmware.** No driver path reads it. What would settle it: the CST8xx register map's identification bytes over I²C while the wheel is idle, `i2cget -f -y 2 0x15 0xa7` (chip ID), `0xa8` (project) and `0xa9` (firmware version). That map is the CST816's, an inference for these chips; run the same three reads on the touchscreen first (`i2cget -f -y 3 0x15 ...`, see [hardware: I²C](hardware.md#buses-and-pins) for why 0x15 on bus 3) and check them against `hyntpfwver` before trusting the wheel's. They are reads, but they race the driver's own transfers on the bus, so take them with the screen off and nothing touched.
- **U-Boot.** It lives in `mtd0` (1 MB) and is not in stock's `update.tar`, so neither the ZIP nor a build shows it. A read of the partition settles it: `dd if=/dev/mtd0 bs=64k count=16 2>/dev/null | strings | grep -m3 -E 'U-Boot [0-9]{4}'` (reading an MTD character device changes nothing); `cat /proc/cmdline` shows what it passed to the kernel.
- **The Wi-Fi module's exact part.** The teardown photo's print reads as FN-Link 6233A-SRB; a sharp photo settles it, and with it the module's rated transmit power ([hardware](hardware.md)).
