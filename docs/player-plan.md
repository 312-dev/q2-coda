# The new player: design and plan

`q2player` replaces stock's `hciplayer`: built from source in `player/`, on current libraries, speaking the socket protocol `demo` already uses, with Q2 Muse's player fixes written as code where they are binary patches today. [player.md](player.md) describes the program it replaces and is the specification for everything below; read it first.

**Status (2026-11-18).** Phases 1 to 5 are done on the host and in the emulator, and phase 7 is done: `q2player` is the player and stock's hciplayer, its patches and its fallback are gone. Left: phase 6, on a Q2.

**The rule of scope: parity.** Whatever stock's player does that demo or a user relies on, the new one does: every format, DSD in all three modes, SACD ISO, QQ Music, CUE, gapless, crossfade, the EQs, ReplayGain, every output, every stream source, and the socket byte for byte as far as demo reads it. demo is not changed. A difference from stock is allowed only when it is in [Deviations](#deviations), and the plan is finished when every row of the [Parity checklist](#parity-checklist) is verified.

The root filesystem held 50,688,000 bytes (the stock image's size, the build's limit until mtd2's own size replaced it: 75,497,472, `ROOTFS_ROOM`) and this branch's `--dev` build uses 49,860,608 since the rebuilt third-party libraries merged (48,836,608 before), so 827,392 were free then. While both players ship (phases 2 to 6) the build grows by `q2player`: phase 2's `--dev --new-player` build measured 50,479,104 bytes, 208,896 to spare, phase 3's 51,515,392, 827,392 too many, and with FFmpeg trimmed ([Risks](#risks)) 51,298,304, 610,304 too many: the build stopped with the overshoot named past 50,688,000, the limit then. With the fallback hciplayer stored xz-compressed ([Risks](#risks), chosen by the coordinator overnight, for the user's review) it is 50,032,640, 655,360 to spare, and with phase 5's TLS and stream code 50,257,920, 430,080 to spare. Once hciplayer goes (phase 7) the build is about 2.6 MB smaller than today, and `libmad.so.0.2.1` (95,152 bytes; only hciplayer needs it) goes too.

**Why FFmpeg and not one decoder library per format.** The list of formats is long (about twenty codecs and a dozen containers) and stock already answers it with FFmpeg, so FFmpeg alone gives parity in one dependency, one license (LGPL 2.1 or later for everything chosen; GPL 3 takes it) and one place to follow security releases. The price is paid once: FFmpeg's decoders are not the fastest for FLAC or MP3 on a CPU without assembly, and its float decoders need care to be exact (below). Dedicated libraries (libFLAC, minimp3, libopus) would cost a demuxer and a build recipe each, and still leave APE, WMA, ALAC, DTS, TAK and DSD to FFmpeg.

**MPEG audio uses FFmpeg's integer decoder** (`mp3`, `mp2`, `mp1`), not its float one: it puts out 16 bits, as stock's libmad does, so MP3 keeps the output format stock opens for it, and its arithmetic is integers alone.

**Why 7.1.** It is a maintained release branch (7.1.5 is its newest release, pinned by SHA-256 in `tools/player.py`; check the release's signature against the FFmpeg key in `docs/third-party.md` when `sec/libs` merges) and the Q2's toolchain, GCC 9.3, builds it without a patch. 8.x and 9.x were not tried with that compiler; a later phase can, and moving is a change to one tuple and a rerun of the exactness tests.

**Compiler flags.** The toolchain and flags are `tools/thirdparty.py`'s, unchanged: Codescape GNU Tools 2020.06-01, `-EL -march=mips32r2 -mabi=32 -mhard-float -mfp64 -mnan=2008 -mabs=2008`, which gives stock's ELF flags (`0x70001405`, checked on the built binary) and loads against stock's glibc 2.28. The X2000 has two XBurst II cores at 1.2 GHz with an FPU; the kernel is built with MSA support, which does not say the CPU has it ([player.md: Open questions](player.md#open-questions)). The plan does not depend on MSA: FFmpeg is configured `--disable-asm`, so the same C runs on the Q2 and on the machine that makes the reference decodes, and integer and IEEE float arithmetic give the same samples on both. That is what makes "bit-exact" testable without a device. If phase 6 measures too little headroom, FFmpeg's MIPS FPU and MSA code can be turned on per decoder, each one checked against the C output first.

**CPU.** No Q2 was available, so the only measurement is relative: both players under the same `qemu-mipsel` user-mode emulator, playing the same files in real time, by the CPU time the emulator used (`# cpu` in each transcript).

| Played in real time | stock hciplayer | Q2 Muse's hciplayer | q2player |
| --- | --- | --- | --- |
| 16-bit 44.1 kHz FLAC, two files, 40 s | 0.45 s | 0.21 s | 0.33 s |
| 24-bit 96 kHz FLAC, 15 s | 0.43 s | 0.18 s | 0.25 s |
| MP3 (LAME V2), two files, 40 s | 0.50 s | 0.36 s | 0.72 s |
| nothing, for 4 s (start-up alone) | not measured | not measured | 0.02 s |

Emulated time is not device time, the tick is 10 ms, and each figure is under 2% of one emulated core, so this ranks nothing finely. What it shows: FLAC costs the new player less than stock and more than Q2 Muse's player (which sleeps where stock polls); MP3 costs it more than either, 1.4 times stock's libmad, which is the one decoder to look at first on a device; and none of the three cases is near a limit with no assembly at all. Device figures are phase 6's first task; the budget to meet there is stock's own load at each rate plus no more than a fifth, and under half of one core at 384 kHz.

**RAM.** 128 MB, no swap. The player's own buffers are small: FFmpeg's probe and packet buffers (about 1 MB), one decoded block, a preloaded second file's context, and the ALSA ring (500 ms; 384 kHz stereo S32 is 1.5 MB). Crossfade's hold is the large one, 6 MB today, and stays that. Streams take the cache demo asks for (512 KB to 4 MB). Phase 6 measures resident size against hciplayer's.

## Architecture

```
demo --- /tmp/sock_play ---> command thread (ipc.c) ---> ctl (requests, settings, status; one mutex)
            ^ answers, events                                  | wake
            |                                                  v
            +------------------------------------- playback thread (engine.c)
                                                    source -> DSP chain -> output
                                   preload thread: opens the next source while the current one plays
```

- **One process, three threads**, as stock: commands, playback, and a preload thread started per `set-gapless`. The command thread never blocks on the playback thread: queries are answered from `ctl` under its mutex, and everything else sets a request and wakes the playback thread. That is also why a query between two songs cannot fault ([internals: Music info between songs](internals.md#music-info-between-songs)).
- **Idle and paused, the playback thread sleeps on a condition variable.** No polling, so the player costs nothing while stopped ([internals: Battery](internals.md#battery)).
- **`source` (source.c)** is one file or stream: `libavformat` demuxes, `libavcodec` decodes, and the result is interleaved PCM in the width the output is opened with. Encoder delay and padding are cut by FFmpeg from the container's own data. A seek goes to the packet at or before the target and drops samples up to it, so it lands on the sample asked for.
- **Custom I/O** sits under `libavformat` for streams and the two vendor formats: a URL is read through `stream.c`'s cache ([player.md: Streams](player.md#streams)), QQ Music is an `AVIOContext` whose read decrypts each block by its offset through `libQMDecryption.so`'s three calls (`qq.c`, the library loaded with `dlopen` on first use, so a root filesystem without it still plays everything else), and an SACD image's stereo area is presented as a DSDIFF file (`sacd.c`).
- **DSP chain** (`dsp.c`), one per song, in this order, each stage absent when its setting is off: ReplayGain, PEQ or 3EQ (`patch/peq.c`, Q2 Muse's own engine, compiled into the player as it is into the payload), Mono Audio, Swap L/R, crossfade (hold and equal-power mix), AirPlay's tap; then, in `output.c`, software volume (Bluetooth, and USB as `mcl-setvol` and `mcl-softvolflag` say) and rate conversion (Bluetooth). With every stage off the decoder's integers go to the output untouched: that path has no float in it and is the bit-exact one. With any stage on, samples are float from the first stage to a single conversion at the end, which rounds and saturates as hciplayer's converters do (16 bits: `lrintf(x * 32768)`, clipped). DSD bypasses the chain, as stock. The level meter reads what is written, after the chain.
- **Scan at speed** (`stretch.c`, `engine.c`): Q2 Muse's `mcl-scan`, a held Previous or Next heard at 2 to 8 times forward or backward at the song's pitch, between the source and the DSP chain ([player.md: Scan](player.md#scan)).
- **`output` (output.c)** opens ALSA as stock does: the device by output way and hardware type, the file's rate with ALSA's resampling off, 500 ms in 16 periods; Bluetooth at its transport's rate, the song resampled to it; another format where a device refuses the song's. It stays open across a change when rate, channels and width are the same, on every output, and on Bluetooth across a change of rate. It does the software volume, and DSD as DoP or Native comes to it already packed (`dsd.c`). It owns the DAC's side too (`/dev/shanling_dac`: PCM or DSD mode per song, mute before a drop or reopen, unmute and the 90-100 ms wait before sound) so the waits Q2 Muse patches in are simply the order of calls.
- **State on disk** is what the patched player reads today, in the same files and formats, so the payload's UI needs no change: `/mnt/data/peq-active` (`Q2PEQ03`, read at each song and again at each `mcl-seteq`, which the payload sends after each change), `/tmp/q2xfade`, `/tmp/q2mono`, `/tmp/q2swap`, AirPlay's `/tmp/q2cast`, and `/tmp/q2press`. q2player adds one of its own, `/tmp/q2clicks`, there while it is the player, for the Clicker below.

### The Clicker

System settings → Controls → Clicker (`patch/clicker.c`, [internals: Key Tone](internals.md#key-tone)): Speaker, Headphones, Both (the default) or Off. Speaker is Key Tone as it was, the MCU's buzzer, silent while headphones, Bluetooth or a USB DAC listen. Headphones has q2player mix a click into what it plays; Both has that and the buzzer whatever listens.

- **The command.** At each click `ringnav_buzzer` decides (once per row moved, once per button press), the payload sends `{mcl-click\wheel}`, `{mcl-click\button}` or, reserved for an alert, `{mcl-click\beep}` on the player's socket (`MSG_DONTWAIT | MSG_NOSIGNAL`, so a busy or dead player never stalls demo). It sends only while q2player is the player, which `/tmp/q2clicks` says (made at q2player's start, removed by the fallback before it runs hciplayer; looked for once a second), a song playing, paused or none; the chirp only while a song plays. q2player takes it unless a song is opening or asked for (`ipc.c`); stock's hciplayer ignores the command, as it ignores any name it does not know.
- **The sounds.** After Rockbox's iPod piezo (`firmware/target/arm/ipod/piezo.c`, Hz = 91225 / period): a wheel click about 1,000 Hz for 4 ms, a button's about 1,820 Hz for 3 ms, an alert about 2,280 Hz for 200 ms. Each is synthesized, a pulse exciting a small resonator: a sine at the pitch dying away with its time constant (1.2, 0.9 and 60 ms), with a 0.25 ms rise and a 0.5 ms fall, at -20 dBFS peak. All are named constants in `player/output.c` (`SOUNDS`, `CLICK_DB`, `CLICK_ATTACK_MS`, `CLICK_TAPER_MS`), to be tuned by ear. And the plug-in chirp, `{mcl-click\charge}` (`patch/charging.c` at a cable in, `clicker_chirp`, under Headphones or Both, while a song plays; never the buzzer, which can only click): `design/mockups/charge_chimes2.py`'s "8-click-up-chirp", a 3 ms tick of low-passed noise (a seeded LCG's, so it is the same each time), then 880 Hz and 1320 Hz blips with their second harmonic at 30 and 90 ms, 340 ms in all, its peak at -12 dBFS (`chirp_at`, `CHIRP_*`; `test_chirp`).
- **The mix.** `output.c` keeps a copy of what it has written, as long as the PCM's buffer. A click rewinds the PCM to `CLICK_LEAD_MS` (20 ms) past what is playing (`snd_pcm_rewind`, as far as `snd_pcm_rewindable` allows), mixes the click into its copy of those frames and writes them again; where nothing can be rewound it starts in the next frames written, up to the buffer late. The mix makes room for the click, `y = x * (1 - e) + e * s` with `e` the envelope (at most the level) and `|s| <= 1`, so a sample within full scale stays within it and the final conversion never clips. Its level is its own: the software volume (Bluetooth with Link Volume off, a USB DAC with `mcl-softvolflag` 1) scales the music before the mix and never the click (`test_click_volume`), so the click is -20 dBFS of the PCM whatever that volume. What comes after the PCM scales both: the headphone DAC's hardware volume, a USB DAC's own, a headset's own (AVRCP absolute volume, set by Link Volume; the Q2 knows the value it sent but not the headset's taper, so the click is not compensated for it).
- **Idle** (`engine.c` `click_session`, `output.c` `output_hold` and `output_idle_*`). With a song paused, its PCM is the click's: the frames written and not yet heard (up to the buffer, half a second) are taken back from the output's copy and the PCM dropped, so it runs empty; on the resume they are written again first and the song goes on from the frame it paused on (`test_click_idle`). A song paused on Bluetooth past `BT_PAUSE_MS` has no PCM ([internals: Bluetooth pause](internals.md#bluetooth-pause)): one is opened for the click at the song's format, left empty and paused, and taken the same way (`test_bt_pause_releases_the_pcm`, `test_click_idle_alsa` `bt-reopened`). With none, a PCM is opened for the click, 48 kHz stereo S16 on the output demo chose (the type of the last song's device), held for `CLICK_HOLD_MS` (3 s) after the last click and closed. Meanwhile silence is written 30 ms apart, 80 ms ahead of what plays (`IDLE_AHEAD_MS`: more than a period, so the PCM starts), counted in the PCM's own ring (its size less `snd_pcm_avail`, `output.c` `idle_ahead`) and not by `snd_pcm_delay`, to which bluealsa's plugin adds the headset's own delay whether the PCM has started or not (its `Delay`, 280 ms on the Pixel Buds: measured that way the fill wrote nothing on Bluetooth, the PCM never started, and no click was heard paused or stopped until 2026-11-24; `test_click_idle_alsa`), and each click goes into it as into a song, so a turn of the wheel does not start and stop an A2DP stream at each tick; bluealsa's `--keep-alive=5` then holds the transport 5 s more after the close. A song asked for, a resume, a stop, a seek, a preload or another output ends it at once, the silence dropped. On the headphone DAC the line is unmuted for it (its 130 ms release waited for, as at a press) and muted after. A PCM that will not open (Bluetooth chosen, no headset's PCM yet, or Radio's receiver holding bluealsa's one client) is not tried again for 10 s. Each session ends with a line in the unified log, its clicks and the frames of silence written for them (`q2player: 2 clicks paused on way 1, 7680 frames of silence written for them`), a warning when none were. A codec switch under it is `bt_reopen`'s, as under a song. The first click is late by what opening costs: on the DAC the 130 ms release; on Bluetooth the plugin's open and bluealsa's Acquire (an AVDTP Start to the headset, not measured), then the encoder (fdk-aac's 1,600 samples, 33 ms at 48 kHz) and the headset's own buffer (bluealsa's `Delay`, 280 ms on the Pixel Buds), so roughly 0.4 to 0.6 s; later ones in the hold, 20 to 80 ms past what plays (as far as the plugin rewinds) plus the same 0.31 s. The iPods that offered Headphones (before the 2009 classic) clicked in the headphones paused as well.

**The fallback** while both players shipped (phase 7's first step to its second): `q2player` ran Q2 Muse's patched hciplayer, stored xz-compressed, when Settings > General > Player said Stock or after three crashes in a row in a boot. Phase 7's second step removed it with the stock player; each crash is still counted and logged ([internals: Player crashes](internals.md#player-crashes)).

### 7. Switch over

## Testing

- **Exactness (host).** The reference for a file is the system `ffmpeg` with its assembly off (`-cpuflags 0`) writing raw PCM: an independent build of the same C arithmetic. The player's output must be those bytes: for lossless formats that is the audio itself; for MP3 it is the integer decoder's 16 bits; for float decoders it is the decoder's float output, unconverted. A pair of files cut from one signal, played through a preloaded change, must be the two references joined, in one PCM open. `test/player/run.py` has every format `music.py` can make, and a pair for each lossy encoder ([Phase 2 results](#phase-2-results)). For a lossy file the reference is cut to its source's length where ffmpeg leaves an encoder's padding in (M4A).
- **Gapless counts.** The same tests fail on one frame more or less: a 20 s file is 882,000 frames, a pair 1,764,000.
- **Protocol (host).** `test/player/fixtures/` holds transcripts of stock's and Q2 Muse's hciplayer answering `fakedemo.py`'s scenarios under qemu. For each, `q2player` is sent the same commands at the same times and must give the same events and query answers in the same order, the same `media-info` fields (bitrate within 2%), and positions within 2 s at each second sampled. A fixture the new player is meant to differ from is listed in `KNOWN` with its deviation.
- **Emulator.** The MIPS binary in the stock root filesystem under qemu, against stock's ALSA library, driven by the same scenarios; its PCM, captured at `snd_pcm_writei`, is compared with the host reference.
- **None of it needs the stock ZIP**, except the emulator runs, which need an unpacked root filesystem.

## Deviations

Each is a difference from stock V1.36's hciplayer, and why. Q2 Muse's existing fixes are in [player.md: What Q2 Muse patches](player.md#what-q2-muse-patches) and count as parity, not as deviations.

| Deviation | Why |
| --- | --- |
| FFmpeg 7.1.5, mbedTLS 3.6.7, no libmad and no OpenSSL 1.0.1 | stock's FFmpeg 3.0 and OpenSSL 1.0.1 are years out of maintenance and parse every file and stream played |
| <a id="a-failure-already-replaced"></a>A song that fails once demo has already replaced it (a `set-songurl` or `mcl-stop` waiting when its open or its output's write fails) is logged (`play failed, already replaced`, `open failed, already replaced`) and not reported: no `{player-status\error}`, no `/tmp/notsupport` | stock reports every failure, and demo's error dialog (`on_wm_timer_dialog`) then calls `player_next_music`, which starts the next song playing with the DAC powered (`config_outputchannel(.., 2)`, `g_dacoff_time` 0) whatever demo had just asked. On 2026-11-21 a Bluetooth headset lost mid-song held the write in `bt_reopen` for 5 s while demo reloaded the song paused; the late failure started the next song, and the DAC stayed on under a paused Now Playing until the next connection, about 1 h 25 min. A song that fails with nothing waiting is reported as before (`test/player/run.py` `test_a_failure_already_replaced_is_not_reported`) |
| No Matroska, MPEG-TS, HLS, W64, TTA, E-AC-3 or DTS-HD demuxing, and no E-AC-3, TTA or LATM AAC decoding | none is a format demo lists ([player.md: Formats](player.md#formats)) or a source hands the player: Tidal, DLNA and the phone's push send one file's URL, and Internet Radio does not use the player. Stock's full FFmpeg 3.0 would open them; leaving them out keeps both players in the root filesystem |
| MP3 decoded by FFmpeg's integer decoder, not libmad | one decoder stack; both put out 16 bits, and the samples differ in the last bit, as any two MP3 decoders' do |
| `https` checks the server's name and chain | stock's checks neither, so a stream could be replaced by anyone on the network path; Q2 Muse's checks the chain against `/etc/ssl/certs/ca-certificates.crt` (Mozilla's bundle, [internals: Stock HTTPS](internals.md#stock-https)) but not the name. q2player checks both against the same bundle, and no certificate's dates, as the image's libcurl (mbedTLS without `MBEDTLS_HAVE_TIME_DATE`), so a wrong clock does not stop Tidal. A certificate for another name, which Q2 Muse's played, is refused (`notfile`, as Q2 Muse's refusal) |
| A message split across two `recv`s is put together | stock drops it. demo sends each message in one `send`, so this only matters under load |
| No start-up check of the unit record (`mtd_debug read /dev/mtd5`) | it protects nothing of the player's; demo makes its own check |
| No watchdog exit when the playback thread is busy | stock kills itself when its main loop stalls; the new player's command thread never waits on playback, so a stall cannot block demo |
| `mcl-mqadecodemode` is stored and unused | as stock, where nothing reads it; listed so nobody looks for the feature |
| `mcl-playspeed` is stored and unused | stock plays 1, 2 and 3 at 1.25, 1.5 and 2 times through `scaletempo`, from a file's start and only at 48 kHz or less ([player.md: Commands](player.md#commands)); q2player's stretch (`player/stretch.c`, [player.md: Scan](player.md#scan)) could play it, not yet wired to it |
| `mcl-scan` | Q2 Muse's own: a held Previous or Next heard at 2 to 8 times, forward or backward, at the song's pitch ([player.md: Scan](player.md#scan)); stock's player ignores it and scans by jumps |
| The stock ten-band `mcl-seteq` filter is not kept | Q2 Muse already replaces it with its own filter and uses `mcl-seteq` only as a signal; the ten gains are ignored there too |
| The PCM stays open across any same-format change, on the DAC as on USB and Bluetooth | stock and Q2 Muse do on some paths and reopen on others; reopening is where the cut starts and lost tails come from. Phase 6 confirms on a device that nothing relied on the reopen |
| On Bluetooth a write that finds bluealsa's PCM gone (`-ENODEV`) opens it again and writes on | a codec switch (the link monitor's step-down, bluealsa's `SelectCodec`) replaces the transport and closes the PCM under the player, and bluealsa starts the new one's encoder only when a client opens it; stock never met it, as its Quality change takes another path, and ended the song as on any error ([internals: Bluetooth link monitor](internals.md#bluetooth-link-monitor), `bt_reopen` in `player/output.c`) |
| Seeks and start offsets (`ss=`) land on the exact sample | stock's land on a frame boundary near it (Q2 Muse's start at 7 s of a FLAC gave 36 frames fewer); nothing depends on the error |
| `ready` lasts until the song's first frame is heard: a few ms after a start on a Q2's card, and on a preloaded change until the song before has played out of the PCM | stock's lasts about 600 ms after a start and 400 ms after a change under qemu, its own opening time. demo treats `ready` and `playing` alike (`0x5bad38` sets `mcl+0x2e` for both), and the payload reads neither |
| WavPack at 24 bits reports `BITS` 24 | stock says 32 (captured); it is display only, and 24 is the file's |
| A DTS stream stock refuses plays | stock answers `error` for FFmpeg's own encoder's `.dts` (captured); FFmpeg 7.1 decodes it bit for bit as the reference does |
| A WMA file's position starts at 0 | stock's starts at the ASF preroll, about 3 s on, so demo's `set-gapless` and Crossfade's hold came 3 s early ([internals: Forced EOF](internals.md#forced-eof)) |
| 24-bit WAV goes to ALSA as `S32_LE`, AIFF as `S16_LE` or `S32_LE` | stock asks for `S24_3LE`, `S16_BE`, `S24_3BE` and `S32_BE` (captured). On the DAC `default`'s `plug` converts either to the hardware's format, so the DAC is given the same samples; a USB DAC, with no `plug`, that refuses one is offered the next format (below) |
| An MP3 whose Xing count FFmpeg distrusts (much shorter than the file) ends at exactly its count when no MPEG frames follow it | Q2 Muse's player ends it once the position is a second past, about 0.3 s of the junk heard; frames that chain at the count (two files joined, a stale count) play on in both |
| The EQ, crossfade, Mono Audio, Swap L/R and the taps act on their files whether or not an `mcl-seteq` has come | hciplayer runs Q2 Muse's filter only once demo's `mcl-seteq` (the EQ on at boot, `peq_stock_eq`) or `patch/crossfade.c`'s `peq_chain` has put it in the chain: Q2 Muse's played a PEQ state with none unfiltered (captured). The payload sends it whenever a state or a fade is on, so in use nothing differs, and the player is not left silent on a lost message |
| With every stage off, the level meter reads a song without changing it | hciplayer's filter, once in the chain (for a fade, Mono Audio or AirPlay), turns every block to float and back, which keeps 16 and 24 bits and drops the low 8 of a 32-bit integer file |
| The level meter measures the first 480 bytes of each decoded block | stock's measures each ALSA write's (`0x43a778`): the same rule over another window of the same music, so a reading can differ by about a dB on music whose peak moves; nothing in Q2 Muse asks for it |
| `mcl-getspectrum` answers twelve zeros | stock runs an FFT into twelve bands (`0x43962c`) for demo's spectrum page, which Q2 Muse leaves out with the VU page, the only callers of the meters (`spectrum_page_init`, `vu_page_init` and their timers) |
| ReplayGain's factor is worked out once in double | stock goes through float, to dB and back (`0x4282c0`, MPlayer's volume filter): the same scale to about one part in a million |
| The Clicker's click in the headphones (Headphones and Both) | new: hciplayer has no way to it ([internals: Key Tone](internals.md#key-tone)). Mixed into a song playing, and with a song paused or none played in silence of its own, as the iPods that had the setting (before the 2009 classic) clicked in the headphones paused as well. Both is the default, so with headphones in the buzzer clicks too, where before it did only with Click With Headphones, off by default |
| Native DSD plays, as `DSD_U32_BE` | stock asks ALSA for format 31, `SND_PCM_FORMAT_SPECIAL`, which a device refuses, and plays nothing (captured); `DSD_U32_BE` is the format ALSA's USB driver offers for native DSD |
| D2P is FFmpeg's DSD decoder, float at the DSD rate over 8 | stock's is MPD's `pcm_dsd`, 16 bits at the same rate (captured): the same tone, more of its resolution kept; a USB DAC without `FLOAT_LE` is given `S32_LE`, `S24_3LE` or `S16_LE` (below) |
| Bluetooth's resampler runs on float, and what it holds back is played at a song's end and at a change of rate | stock's runs on the song's format and drops it (18 frames lost at a gapless change, captured; Q2 Muse's 9); a pause keeps the resampler's state, where stock starts a fresh one |
| A USB DAC that refuses a song's format is offered `S32_LE`, `S24_3LE`, then `S16_LE` for a song wider than 16 bits | stock offers `S16_LE` then `S32_LE`, so a DAC without `S32_LE` got 16 bits of a 24-bit song |
| A level below 0 from `mcl-setvol` (R well below L) is silence | stock takes its dB, which is not a number, and its right channel was 8.4 times louder (captured); demo sends L and R equal |
| A stream starts once `P` percent of its cache is in | the same rule as stock's MPlayer (a FLAC from a slow server starts at the same time from both, captured), but stock's WAV demuxer first looks at the file's end, a reconnect each, so a WAV from a server slower than it plays started 8 to 10 s on and one with a stall after it (captured); q2player starts at the fill and waits in the stall |
| A FLAC stream's seek near its end plays to the end | stock and Q2 Muse's end it half a second on (captured): Q2 Muse's fix for files does not reach a stream |
| A stream cut short ends about a second after its last byte | FFmpeg's reconnect tries twice more (at once, then after a second) before the end; stock's ends at once (captured) |
| An area of an SACD image is read by `player/sacd.c`, not `libsacd.so` | the same frames and the same bytes out (captured); stock's player never called the library, and its API is sacd-ripper's ripping interface |
| A skip on Bluetooth or USB keeps the PCM open when the format is the same | stock drains, closes and reopens it at every skip (captured), the case of the row above on the PCM kept open |

A candidate that is **not** adopted without a ruling: MP3 through FFmpeg's float decoder, written as float like AAC and Vorbis. It keeps what 16-bit rounding discards, but it changes the format the DAC is opened with for most of a library and `BITS` in `media-info` from 16 to 32. Parity keeps the integer decoder.

## Risks

- **demo in the emulator** plays since phase 2: the empty Folder page was the guest's `readdir` failing on the host's 64-bit directory offsets under qemu-user, fixed in the emulator's shim. A later phase's real-demo runs need the emulator copy with that fix ([player.md: Capturing](player.md#capturing)).
- **Float decoders on the device.** For AAC, Vorbis, Opus and the other float decoders, exactness rests on the X2000's FPU being IEEE, as the ABI assumes (FLAC, the other lossless formats and MP3 use integers alone). Already under qemu the MIPS build's AAC, Opus and WMA differ from this machine's in the last place of a few samples in a thousand, while Vorbis, AC-3 and DTS do not. Not established why: the guest's glibc 2.28 `libm` against the host's (tables FFmpeg computes at init with `sin`, `cos`, `pow`), or GCC contracting multiplies and adds into `madd.s` on MIPS. A MIPS build with `-ffp-contract=off` under the same emulator settles the second; a capture on a Q2 settles what the device does. Phase 6's first test plays the reference files and compares a USB or loopback capture, or the PCM logged by an `LD_PRELOAD` as the emulator's shim does.
- **Space while both players ship.** The rebuilt third-party libraries took the 0.2 MB that phase 2 had spare and 0.8 MB more: a `--dev --new-player` build was 827,392 bytes over after the merge (phase 3 results). q2player's FFmpeg is now trimmed to what [player.md: Formats](player.md#formats) and the player's sources need, measured in the squashfs bytes `q2player` takes (LZO 9, 128 KB blocks, as the build packs it): no W64, E-AC-3, DTS-HD, Matroska, MPEG-TS, HLS or TTA (1,655,297 to 1,542,723), and each function in its own section for the link's `--gc-sections` (to 1,437,093): 218,204 in all, and the image 51,298,304 bytes, still 610,304 over. Nothing a listed format needs is left to cut: what remains is the decoders (DTS's tables alone are about 360 KB of code and data) and FFmpeg's transform tables, which only a patch to FFmpeg could drop. Measured, not chosen (it is a ruling on what a dev image carries): FFmpeg's `--enable-small` (`-Os` and its smaller code paths) takes `q2player` to 1,051,859, 385,234 more, still about 225,000 over, and changes the compiled code, so every exactness test would have to be run again; the fallback hciplayer xz-compressed (`xz -9e`, unpacked by BusyBox's `unxz`, which both the stock and the rebuilt BusyBox have, before `player/main.c` runs it) goes from 4,251,546 squashfs bytes to 2,978,339, 1,273,207 less, about 663,000 to spare, enough for phase 5's TLS (221,184) too, at the price of 7.7 MB of `/tmp` (RAM) or a copy on `/mnt/data`, and the unpacking time at each start of the fallback; or the fallback left out of the image once phase 6 has passed on a device (4,251,546, and libmad's 95,152 bytes with it; the Unicorn suites need hciplayer in the image until then). **Chosen by the coordinator overnight, for the user's review: the fallback xz-compressed.** `tools/build.py --new-player` installs it as `/usr/lib/hciplayer-stock/hciplayer.xz` (Python's `lzma`, preset 9 extreme, CRC32 check: 2,978,100 bytes, no BCJ filter, since xz has none for MIPS), and `player/main.c` unpacks it with `/bin/busybox unxz` to `/tmp/hciplayer-stock/hciplayer` when the switch selects it. The image is 50,032,640 bytes, 655,360 to spare. Where: `/tmp`, a tmpfs mounted by stock's `/etc/fstab` with no `size=`, so the kernel's default of half the RAM, about 64 MB on a 128 MB Q2 (device: `df /tmp`), against the 7.7 MB the file takes; `/mnt/data` (UBIFS on the internal flash) is not needed and would wear the flash at each boot. The cost, while the fallback is the player: 7,708,840 bytes of RAM held in `/tmp` until the next boot (tmpfs pages are not reclaimed without swap; the running hciplayer maps those same pages, so it adds nothing while it runs), and the unpacking before its first start each boot, 0.29 s under `qemu-mipsel` on this machine (device: `time busybox unxz -c /usr/lib/hciplayer-stock/hciplayer.xz > /dev/null`); later starts find the file and pay nothing. With `/mnt/data/q2player` made nothing is unpacked. Proof (emulator, the built image's root filesystem, `--killall 5`): without the switch the process is `/tmp/hciplayer-stock/hciplayer` (`comm` `hciplayer`), the bytes the build compressed, playing (Q2 Muse's `media-info` and `ready`, PCM captured), and `killall -9 hciplayer` ends it (exit 0); with the switch it is `/usr/bin/hciplayer`, q2player, and the same `killall` ends it. **Since phase 7's first step every build, release included, carries both:** the `--dev` image measured 53,604,352 bytes (`rootfs_squashfs_bytes`, 2026-11-17), 21,893,120 under `ROOTFS_ROOM` (75,497,472, mtd2 less its bad-block spare, the limit since the 50,688,000 above), so space no longer bounds the fallback; the compressed copy stays because it costs only RAM, and only while the stock player plays.
- **`default` is a `plug`.** Stock relies on it not converting. If a rate or width is not the hardware's, `plug` converts silently; the player asks for no resampling but cannot forbid a width change. Phase 6 reads `hw_params` at each format and, if one is converted, `output.c` asks for the hardware's width itself.
