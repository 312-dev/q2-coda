| --------- | ---------------------------------------------------------------------------- |
| `patch/`  | The firmware payload (C, MIPS assembly, linker script) and the iPod UI audit |

## Requirements

- clang, lld and llvm-objcopy
- squashfs-tools 4.6 or later (tested with 4.6.1 and 4.7.5)
- ImageMagick 6 or 7 for the iPod UI's settings icons (`convert` or `magick`; tested with 6.9.12)
- The test dependencies: `pip install -r requirements.txt`
- For the rebuilt third-party libraries ([third-party.md](third-party.md)): network access on the first build, which fetches the Codescape MIPS toolchain (2.3 GB) and the pinned sources into `~/.cache/q2-thirdparty`, and about an hour to compile them once; bwrap and qemu-mipsel for `test/thirdparty.py`
- Only to change `remote/iroh-sidecar` (`q2-iroh`, which a build otherwise takes pinned from the cache): Rust nightly-2026-11-18 with `rust-src` ([remote: Building it](remote.md#building-it)). On GRAYTHINKPAD it is installed in `~/.cache/q2-rust` (`rustup` and `cargo` there; `~/.cache/q2-rust/wrap/cargo` runs `cargo +nightly` on that nightly). The pinned binary is reproduced byte for byte only with that toolchain and its target folder: `RUSTUP_HOME=~/.cache/q2-rust/rustup CARGO_HOME=~/.cache/q2-rust/cargo PATH=~/.cache/q2-rust/wrap:$PATH CARGO_TARGET_DIR=~/.cache/q2-rust/target python3 tools/iroh.py` (a later nightly, or another target folder, makes a different binary of the same crate). The crate's unit tests run on the host the same way with `cargo +nightly test --offline --release --manifest-path remote/iroh-sidecar/Cargo.toml` and `CARGO_TARGET_DIR=~/.cache/q2-rust/target-host`.
- All of the above come in the native arm64 container that `tools/mac/q2env` runs on the MacBook Pro, the supported build host: [Building on macOS](#building-on-macos)
- The original stock ZIP. Its SHA-256 is:

```text

```

## Build

```sh
python3 tools/build.py 'Q2 Firmware V1.36.zip' --out /tmp/q2-build                 # release build
python3 tools/build.py 'Q2 Firmware V1.36.zip' --out /tmp/q2-dev --dev             # test build
```

Rebuilt firmware uses `assets/boot-logo.jpg` as the boot splash, with the [boot animation](boot.md#boot-animation) in its place in Dark Mode. Pass another 320x375 JPEG with `--logo` to use your own; see [boot.md](boot.md#custom-boot-logo).

The build replaces the stock equalizer page with a 30-band PEQ editor (bands, shelves, preamp, on/off, presets, stock's built-in genre presets, `/EQ` import) and `q2player` plays the matching DSP (`patch/peq.c`). The build also clears the 44.1 kHz AAC capability bit in `bluealsa` (see [internals.md](internals.md#bluetooth-aac)).

### Bundled apps

The build carries the Subsonic card app in the root filesystem ([internals](internals.md#bundled-apps)), from its release zip, pinned in `BUNDLED_APPS` (`tools/build.py`) by version, zip name, size and SHA-256. It reads the zip from `--apps DIR`, `~/.cache/q2-apps` by default, and stops when the file is missing or is not the pinned one. The zip's name carries the q2-subsonic commit it was built from (`q2-subsonic-v1.0-9065736.zip`); make it from q2-subsonic's source at that commit, with a clean tree:

```sh
contrib/shanlingq2/build.sh /tmp/q2-subsonic                 # in q2-subsonic, at the pinned commit
mkdir -p ~/.cache/q2-apps && mv /tmp/q2-subsonic/q2-subsonic-v1.0-9065736.zip ~/.cache/q2-apps/
```

The build refuses a zip named `-dirty` (built from a tree with uncommitted changes), and, when the zip carries a `version` file (q2-subsonic's `build.sh` stamps one, `q2-v1.0+<commit>`), one whose commit is not its name's. Beside the app in the image it writes `/usr/lib/q2apps/<id>/bundle`, which says which build the Q2 carries: the zip, its SHA-256, the program's SHA-256 and the zip's stamp (`-` when it has none). On a Q2, `cat /usr/lib/q2apps/subsonic/bundle` and `sha256sum /usr/lib/q2apps/subsonic/q2-subsonic` answer which commit runs. The build's `manifest.json` (`bundled_apps`) and a release's `release.json` and notes record the same, and `test/build.py --build` checks that the image's program is the pinned zip's, byte for byte.

Subsonic's entry is `builtin`: the firmware's copy is the only one that runs and the App Store does not list it, so a new Subsonic reaches Q2s only in a firmware update. A new version is a new pin, chosen by whoever integrates the app change into the firmware: build its zip at a commit that is on q2-subsonic's remote, then set its version, name, size and SHA-256 in `BUNDLED_APPS`, and release the firmware ([releasing](releasing.md#the-app-list)). The source hash covers the pin, so a build made with the old zip counts as stale. With the current pin (3,738,531 bytes, commit 9065736 on `feat/bt-pace`, which paces its background downloads while Bluetooth shares 2.4 GHz: [internals](internals.md#bluetooth-coexistence-pacing)) a `--dev` build's root filesystem is 55,472,128 bytes (2026-11-25), about 20 MB under the 75,497,472 bytes `rootfs_fits` allows.

### What the rootfs drops

Every build, release and `--dev`, hardens stock's root filesystem (`tools/build.py`):

- **No password login.** Stock's `/etc/shadow` gives root the same password hash on every unit. `lock_root` sets the field to `*`, and the build stops if `password_logins` finds any account a password, or an empty field, would log in to. `/etc/inittab` loses its `getty` on `ttyS3` (`SERIAL_GETTY`), so the board's serial pad shows the boot messages and offers no login. Nothing on the Q2 logs in: `q2remote` runs `/bin/sh` itself.
- **Debugging and network tools** (`DEBUG_TOOLS`, `DEBUG_LINKS` in `OBSOLETE`): `strace`, `strace-log-merge`, `sqlite3` (the program; demo's `libsqlite3` stays), `hcidump`, `memtester` and `nandtest`, and busybox's `telnet`, `tftp`, `inetd`, `dnsd` and `dhcprelay` links. No script, program or library in the rootfs, and nothing in `patch/`, names them as a command; the rootfs's `libcurl` speaks only HTTP, HTTPS and `file` ([third-party](third-party.md#curl-and-mbedtls)).
- **Stock's on-screen keyboard** (`KB_ASSETS`): its page `kb_default_t9`, its style and its ten key images; nothing opens it, which the build checks ([internals](internals.md#the-keyboard)).
- **Stock's Wi-Fi File Transfer server** (thttpd on :8888) never starts: `switch_wifitransport`'s hook refuses it, and Network's row opens LocalSend instead ([localsend](localsend.md#what-it-replaces)).
- **Bluetooth** is discoverable for 180 s after demo turns it on (`BT_DISCOVERABLE` in `/etc/bluetooth/main.conf`), not for as long as it is on.
- **Network time** asks `0.pool.ntp.org` in place of `cn.pool.ntp.org` (`NTP_POOL`, [Clock](internals.md#clock)).
- **Baidu Netdisk's saved sign-in**, `/mnt/data/baidu_token.conf`, is deleted at boot (`BOOT_HOOK`).

`test/build.py --build DIR` checks each against the stock image.

### Stopped-audio notifier wait

Off by default, `--dev --aic-idle-wait` (on by default from 1.5.0 to 1.6.1). The audited audio driver's stopped-state 10 ms polling is replaced by an
event wait, woken by start/resume and teardown. Active PCM notification timing, period and
buffer limits are unchanged. See
[audio-notifier.md](audio-notifier.md) for the exact scope.

```sh
python3 tools/build.py 'Q2 Firmware V1.36.zip' --out /tmp/q2-notifier --dev --aic-idle-wait
```

### FLAC fast paths

On by default: `--flac-experiments sync,lpc,output` (all three). Pass a subset to build only some, or `--flac-experiments ""` for the stock decoder paths. Each is checked against the pinned V1.36 player.

### Versioning

The updater refuses only a firmware whose version literal is identical to the installed one (`update_firmware`, `0x502bd0`; the online check `check_otginfo`, `0x5030f8`). So each build carries a 5-character tag, `VERSION` (`x.y.z`, single digits) and `BETA` (a pre-release's beta number, 0 for the release) packed as `V<xyz><beta>`; a release build stops unless both are single digits. For example, 1.8.0 beta 2 is `V1802` and 1.8.0 is `V1800`, so each beta and then the release installs over the one before. Releases up to 1.8.0 BETA were packed as `V<xyz>I` (1.0.0 was `V100I`). The mod installs over stock and over any other build, and stock V1.36 installs back over it.

About's **Firmware** row (stock's FW. Version) reads the same literal, so it shows the stock firmware's version (`STOCK_VERSION`, from the stock `firmware_v20.info`). A row below it named for the product (`PRODUCT_NAME` in `tools/build.py`, the one place the on-screen name is spelled) shows `<version>`, plus ` beta N` in a beta, or ` dev N` in `--dev` builds. Release tags use the plain version (`1.0.0`); releases up to 1.0 were `V`-prefixed. Each release carries `update.tar`.

`--dev` numbers each test build one past the untracked `.build-number` and the `build-number` in the git directory that every worktree of the checkout shares, and tags it `V` plus that number in three base-36 digits, then `i` (`V001i`, `V002i` … `VZZZi`). No two test builds from one repository's worktrees share a tag (a separate clone counts on its own), and none equals a release's, so the updater installs each test build over the last and the release over any of them. `--dev` applies to that build only: the release procedure never passes it, and the manifest records the build number as `dev` (`false` otherwise).

`--update-repo OWNER/NAME` points **Software Update's** online check and download at another GitHub repo's latest release, and the App Store at that repo's `main` `sources.list`, so a fork's test builds update from the fork's own releases. It defaults to `312-dev/q2-coda`, q2-coda's own; both must be signed by the build's release key (below), so pointing it at upstream's `DiamondBond/q2-pod`, whose releases carry no signature, installs nothing. The manifest records it as `update_repo`, and `tools/release.py` refuses a build that points anywhere else.

Software Update's download and the App Store take only what the q2-coda release key signed ([Release signatures](internals.md#release-signatures)). Every build compiles in that key's public half from `assets/signing/q2-coda-release.pub` and stops without it. `--signing-key PUB.PEM` compiles in another Ed25519 public key instead, for a test build that should take updates and app lists signed by a key whose private half you hold (`openssl genpkey -algorithm ed25519 -out /tmp/dev.pem`, then `openssl pkey -in /tmp/dev.pem -pubout -out /tmp/dev.pub`; keep both out of the repository). It requires `--dev`. The manifest records the key as `signing_key`, and `tools/release.py` refuses a build with any other.

Development builds also start `q2remote`, a key-gated root shell with screenshots and input over Wi-Fi, for developers and agents; see [remote.md](remote.md).

They also run `adbd`, Android's debug daemon, so `adb` gets a root shell, file copies and screenshots over the USB cable once the computer is authorized, from its own USB gadget that gives way to stock's USB storage and DAC; see [adb.md](adb.md). It is built by `tools/thirdparty.py` ([third-party.md](third-party.md#adbd)), and the manifest records its version, SHA-256 and size under `adbd`. Release builds have neither adbd, its gadget script nor the wrapped USB scripts, and `test/build.py --build` checks that.

Off by default, `--dev --rotator-lazy-clock`: the rotator clock is held only from its first conversion. See [clock gating](clock-gating.md) for the exact module guard and tests.

Off by default, `--dev --pwm-idle-clock`: the paired PWM/MCU clock gating. It needs all three matching files and a reboot. See [PWM clock gating](pwm-clock-gating.md) for its ownership protocol and fallbacks.

All three kernel-module experiments were on by default from 1.5.0 to 1.6.1 and went back to `--dev` in 1.6.2: no battery saving was measured for any of them, and none handles suspend/resume, which stock Standby does by default.

`--own-bluez` is off in every build unless given. It adds Vamp's own bluetoothd (upstream BlueZ, built by `tools/thirdparty.py`) at `/usr/lib/vamp-bluez/bluetoothd`, beside stock's and started by nothing. See [bluez](bluez.md#the-build-switch).

`--dev --mcu-idle-sleep` is off in release builds. It adds an interruptible MCU sleep with an explicit wake handshake. See [MCU sleep](mcu-sleep.md).

Every build installs the player, `q2player` ([player-plan.md](player-plan.md)), as `/usr/bin/hciplayer`, where stock's player was, so demo starts and stops it by that name. It builds `q2player` with `tools/player.py` (FFmpeg on first use, some minutes; the toolchain and mbedTLS that `tools/thirdparty.py` keeps in `~/.cache/q2-thirdparty`) against the image's own `libasound.so.2`, and records `q2player_sha256` in the manifest. The root filesystem holds 75,497,472 bytes (`ROOTFS_ROOM`: mtd2 less a bad-block spare, [hardware](hardware.md#flash-layout)): past that the build stops and says by how much.

## Building on macOS

The supported way to build and test is the native arm64 Linux container on the MacBook Pro: `tools/mac/q2env CMD` runs CMD there, in the current directory (no CMD: a shell). The laptop (GRAYTHINKPAD, WSL) path in the rest of this file and in [orchestration](orchestration.md) is no longer maintained.

```sh
B=$(tools/mac/q2env python3 tools/ci/rebuild.py --dev | tail -1)
tools/mac/q2env python3 tools/ci/affected.py --run "$B"              # or --all
```

The image (`tools/mac/Dockerfile`) is Ubuntu 24.04 arm64 with the [Requirements](#requirements) (clang and lld 18.1.3, squashfs-tools 4.6.1, ImageMagick 6.9.12, qemu-user 8.2.2, bwrap 0.9.0, Go 1.22.2, ccache 4.9.1) and a venv of `requirements.txt`, `test/unit/requirements.txt`, pytest-xdist and mypy made from the arm64 PIE Python 3.12.16 that `actions/setup-python` installs ([Firmware tests](#firmware-tests) refuse a non-PIE one). `q2env` builds it on first use and again when the Dockerfile, `tools/mac/cc` or the pinned requirements change.

- **The same paths inside and out.** The Mac's home is mounted at its own path and is `HOME`, and the command runs as the Mac's user, so a worktree, `~/.cache/q2-builds/...` or `~/q2-stock/Q2 Firmware V1.36.zip` (`rebuild.py`'s default ZIP) is the same file in either shell.
- **`~/.cache/q2-thirdparty` is also at `/home/gray/.cache/q2-thirdparty`**, where its components were built, and `Q2_THIRDPARTY_CACHE` names it: `tools/thirdparty.py`'s cache keys and its output's compiler paths include the cache's path (`REPRODUCIBLE`), so only there are they reused and rebuilt to the same bytes.
- **The Codescape MIPS toolchain is x86-64**, the one x86 dependency left. It runs under the Colima VM's Rosetta handler, with the image's amd64 libc: every build runs its `strip` on adbd (`thirdparty.stripped`), and a third-party or q2player recipe that changes compiles with it; the cached outputs in `~/.cache/q2-thirdparty/out` and `~/.cache/q2-player` cover the recipes as they are. Moving these builds to an arm64 toolchain of Vamp OS's own is open. The toolchain is in a Docker volume, `q2-toolchain`, because the Mac's home is case-insensitive APFS and its sysroots hold 136 pairs of paths that differ only in case (`xt_MARK.h` and `xt_mark.h`); `q2env` unpacks `dl/mti-linux-2020.06-01.tar.gz` there once, as `toolchain()` does.
- **`-m32` test programs** (`test/coverflow.py`, `test/peq.py`'s audio writer) are built by `i686-linux-gnu-gcc` (`tools/mac/cc` takes `cc -m32` there) and run under the VM's qemu-i386 against the image's i386 libc. `/tmp` is a 2 GB tmpfs, because on overlayfs a 32-bit program's `readdir` there stops at once with `EOVERFLOW`.
- **Namespaces and `/proc`.** bwrap and `unshare -Ur` need user namespaces: `q2env` turns off Docker's seccomp and AppArmor profiles, and the VM must have `kernel.apparmor_restrict_unprivileged_userns=0`. The [Seam test](#seam-test)'s `unshare --mount-proc` needs `/proc` unmasked (`systempaths=unconfined`).
- **The emulator** ([Emulator pool](#emulator-pool)) execs the MIPS rootfs's programs in a bwrap chroot through a qemu-mipsel binfmt handler at `/usr/libexec/qemu-binfmt/mipsel-binfmt-P`, which the VM registers (below), and `~/q2-emu-server/qemu-mipsel-static` must be the arm64 build, the image's `/usr/bin/qemu-mipsel-static`. The pool's card fixture is `~/.cache/q2-emu-pool/card`.
- **No `q2-heavy`** (no systemd in the container): the gate runs suites bare, and its memory rule (a 4 GB floor) holds against the VM's memory. A failed suite's second try runs with nothing beside it, so one failure serializes the rest of an `--all` run.
- **Core dumps are off** (`--ulimit core=0`).

Colima runs the VM (`~/.colima/default/colima.yaml`): `vmType: vz`, `rosetta: true` (the toolchain), `mountType: virtiofs` with the home mounted writable, 9 CPUs and 11 GB (the Mac has 18 GB, shared with an Ollama model of about 9.4 GB when it is loaded), 80 GB of disk, and system provision steps run at every start:

```yaml
provision:
  - mode: system
    script: echo kernel.apparmor_restrict_unprivileged_userns=0 > /etc/sysctl.d/60-q2-userns.conf && sysctl -q -w kernel.apparmor_restrict_unprivileged_userns=0
  - mode: system
    script: echo ':qemu-mipsel:M:0:\x7f\x45\x4c\x46\x01\x01\x01\x00\x00\x00\x00\x00\x00\x00\x00\x00\x02\x00\x08\x00\x01\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00:\xff\xff\xff\xff\xff\xff\xff\x00\x00\xff\xff\xff\xff\xff\xff\xff\xfe\xff\xff\xff\xff\xff\xff\xff\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x20\x00\x00\x00:/usr/libexec/qemu-binfmt/mipsel-binfmt-P:PO' > /etc/binfmt.d/qemu-mipsel.conf && systemctl restart systemd-binfmt
```

What does not pass there yet:

- **`test/bluealsa.py`'s SBC packets at the MTU are not run on arm64** (`check_mtu` prints that it skips them; the rest of `test/build.py --build` runs and passes). Under Unicorn's arm64 build, 2.1.4 and its dev branch at `8317c39` alike, that one harness run (stock's bluealsa as well as the patched one) leaves `s1` and `s4` 0 after `lw s1, 492(s3)` and `lw s4, 496(s3)` (`0x406274`, `0x406278`) while memory holds 2 and 48000, and the encoder later jumps to 0; x86-64's Unicorn runs it right. The same block alone is right, and it is not the instruction count, the translation cache, range hooks or earlier instances; the cause inside Unicorn is not pinned. It reproduces with `test/bluealsa.py`'s `encode(stock, aptx, SBC, 1021)`, stock's bluealsa and libopenaptx unpacked from any build, in a fresh process. The other Unicorn suites are not affected: `test/patch.py`'s full draw-call trace (`Q2_TRACE`, 1,327,549 lines) of one release build is byte-identical under arm64's and x86-64's Unicorn (2026-11-27), and the trace does tell builds apart (a `--dev` build's differs).
- **The emulator's first lease can miss**, cause not pinned: on 2026-11-26 `test/coda_rc_e2e.py`'s first lease of a new pool copy found no `CARREMOTE=1` in `config.ini` after the boot (its `prepare` writes it before), and one smoke run timed out on Center opening Now Playing (`STEP_S`, 8 s); both passed when run again.
- **`tools/ci/test_orch.py` needs `systemd-run`** (it tests `q2-heavy`'s scopes), which the container has not.

- **MIPS suite:** `test/patch.py` runs `test/patch_suite/`'s files, one per area (`00_machine.py`, the Machine and its mocks, through `18_headset_info_eq.py`), in name order in one namespace, so a later file uses the Machines and state of the earlier ones and none runs alone (which is also why it is run serially: [Fast test runs](#fast-test-runs)). It executes the actual patched payload and the stock key and touch filters under Unicorn. UI services are mocked; the one other mocked boundary is the `system()` call that Key Tone uses to click the speaker. Case coverage lives in `test/patch.py`. Run the payload, headset worker, metadata dispatch and packaging checks for both Stock and iPod builds.
- **Where a machine's hook runs:** `Machine.hook` (the mocks, and what a test's subclass adds) is Python, so Unicorn does not call it at every instruction: a small C filter, compiled as the suite starts (`cc`), calls it at each symbol's address, at each address a mock is set at and anywhere in the mocks' own region (`0x1000000` up). A hook that tests any other address itself (a place inside a stock function) names it first with `watch(address)`, or is never called there. `test/playback.py` and `test/headset_io.py` run the same machine.
- **Draw-call trace:** `Q2_TRACE=FILE python3 test/patch.py BUILD` also writes every draw and widget-property call, each hook's return and each passed case to FILE, by value: payload addresses appear as symbol names (or `P`), stack ones as `S`. Two builds that draw the same give byte-identical files, so `cmp` checks a refactor that should change nothing on screen.
- **Known gap:** the stock rounded vgcanvas branch can't run end to end under Unicorn 2.1.4. Stock is built `-mfp64`, and Unicorn's MIPS32 FPU only implements `FR=0`, so its 64-bit conversions trap. The test runs the branch up to that instruction and asserts the calls before it.
- **Reproducibility:** two fresh builds must produce identical `update.tar` files. Packaging verifies MD5 entries, unchanged kernel and rootfs metadata, and a rootfs no larger than `ROOTFS_ROOM` (72 MiB, [hardware](hardware.md#flash-layout)).
- **Space:** the payload is built with `-Oz` and linked with lld's `-O2`, which stores a string that ends another inside it; LLVM's delay-slot filler also searches a branch's successor blocks and the instructions after it (`FILL`, `tools/build.py`), which leaves about 6,800 fewer `nop`s; and demo's `.pdr` section (MIPS procedure descriptors, 423 KB past every LOAD segment, never read at run time) ships zeroed. mksquashfs packs file tails into fragments (`-tailends`), which saves about 26 KB. For rootfs headroom see [Boot](boot.md#making-a-logo-that-works).
- **Manifest checks:** the runner refuses a `manifest.json` whose `source_sha256` doesn't match the current patch sources, and verifies the stock, patched and payload hashes against it.
- **Guards:** the builder rejects any `patch/contexts.inc` name that isn't a window name in the stock rootfs UI assets, so an allowlist typo can't silently disable a screen. Widget offsets and shared ABI constants live in `patch/offsets.inc`, which both the payload and the test mocks read.
- **Limits:** instruction counts are mocked-service measurements, not hardware latency.

### Seam test

`python3 test/subsonic_seam.py` runs the Subsonic app the firmware carries against `q2-fakesonic`, a scripted server, with the firmware's own C on the other side of every file they share: `.catplay`, `.play` and its queue m3u, `.playing`, `.ahead`, `.stream`, `.radio`, `.coverask-iap` and their answers in the app's state file, the caps line and `/tmp/q2-addon.library`. Three bugs of one week (2026-11-22) passed each program's own tests and lived here: under Repeat All the app never fetched the next song, a queue file past 256 KB was cut at about 2,300 songs, and a Next onto a song still downloading stopped playback. `test/subsonic_contract.py` checks only that both sides still name the same words and files.

- **The app** is a host build of the commit the pinned zip was cut from (`BUNDLED_APPS` in the tree the test runs in, its name's commit; ~/.cache/q2-seam/build/, once per commit), `--commit SHA` another, `--app DIR` a checkout as it is (for the app's developer, before a zip is cut), or `--mips QEMU` the zip's own MIPS program under qemu-mipsel. Its card files (`q2app`, `run`) are the zip's: `--commit`'s own when `~/.cache/q2-apps` has it.
- **The server** is `cmd/q2-fakesonic` from the q2-subsonic commit `FAKESONIC` names (the harness, which older app commits lack): a library of `-songs` in albums of `-album`, Range on every song, covers, and a control socket that cuts a song's download at a byte and holds it (`/cut`), slows a call (`/delay`) or sends a song at a set pace (`/rate`).
- **Isolation.** Each test runs the app and the server in a user, mount and network namespace of their own (`unshare -Urmn`): the test's root `card/` is their `/mnt/mmc`, its `tmp/` their `/tmp`, and the server is on `10.77.0.1:4533` on the namespace's own loopback, an RFC 1918 address the app takes `http://` to and a port no other agent can hold. The firmware's side (`test/fw/seam.py`) is test/fw's library with its file calls on the same files (a firmware path is always mapped under the root), stock's queue, Now Playing, player and SQLite stood in for as test/fw's own tests do, on the real clock. Every wait polls for a state with a deadline.
- **Scenarios** (`test/fw/test_seam_subsonic.py`): an album started from the Library (the catalogue imported into SQLite by catalogue.c, the press through `catalogue_load`) whose next songs are fetched ahead; Next onto a song the server holds back, which waits and plays; Repeat All, stock's and Shuffle Songs', once every downloaded song has played; the owner's 9,199-song list across the app's moving 1,000-song window (an Up Next tap to its end, Next past its edge, Previous back) and shuffled whole; a download cut mid-song that stalls and resumes with Range; a `.coverask-iap` answered while a song downloads; Radio started, stopped and started again, and a slow Radio that does not replace a later list; a song pressed from a slow server, whose amount on Now Playing (`np_stream_loading`) counts up while it downloads. It found two bugs, both since fixed and kept as tests: under Shuffle, Next on the queue's last song played the list's next instead of Up Next's first, and Download Ahead Off still fetched two songs at a list's start.
- **Proved on the bugs:** against q2-subsonic `32bd2cd` (the pin before `132e232`) seven of the nine fail, each for its bug (the window, Range, `.coverask-iap`, the slow Radio, both Repeat Alls); against `132e232` all pass, in about 75 s, about 140 s on a busy machine.

## Fast test runs

For many branches at once on one machine. The tools are in `tools/ci/` (outside `source_sha256`, so editing one does not make a build stale); their own checks run with `python3 -m pytest tools/ci -q`. How work flows through them, from a worker's first edit to a release image, is [orchestration](orchestration.md).

```sh
B=$(python3 tools/ci/rebuild.py --dev | tail -1)   # this worktree's build, reused when nothing changed
python3 tools/ci/affected.py                       # what this branch's changes need, against the trunk
python3 tools/ci/affected.py --run "$B"            # and run it, the suites at once: test/patch.py whole is one serial process
python3 tools/ci/fw.py                             # all of test/fw on xdist workers; --asan for the sanitizers
python3 tools/ci/merge_batch.py --mark-ready       # this branch is green and merges cleanly: queue it
python3 tools/ci/gate.py                           # a release's gate: one build, every suite at once
python3 tools/ci/merge_queue.py status             # the queue: what is ready, what is running, the last events
python3 tools/ci/emu_pool.py get "$B"              # borrow a shared emulator (see Emulator pool)
python3 tools/ci/smoke.py "$B"                     # walk the build's UI on a pooled emulator (see Smoke test)
q2 status                                          # the queue, workers, heavy jobs, old shells, the machine
q2-wait --pid PID --timeout 600                    # wait for a process or a log line, never without a limit
```

- **What a branch runs** (`affected.py`): the tests its changed files map to. A change to the payload (`patch/`, a build input in `tools/`, `assets/`) runs all of `test/patch.py`, which runs the payload as one program; an edit to `test/patch.py` runs only the tests (`passed()` to `passed()`) holding a changed line or naming a changed helper; `patch/X.c` runs the `test/fw` files that name `X.c`, its `X__` statics or a function it defines, plus the end-to-end files, or all of `test/fw` when none does, and the `test/unit` files that name `X.c`; `patch/coverflow*.c` and `.h`, `home.c`, `page_parallax.c` and `playlist_art.c` also run `test/coverflow.py` (host build of the Coverflow code with stand-ins for the others); a file in a folder a `test/unit` file checks whole (`SCANNERS`: `test_theme.py`'s and `test_art.py`'s rules over every `patch/` source, `test_docs.py`'s citations in `patch/`, `tools/` and `test/`) runs that test too; a `.py` under `tools/` or `test/unit/` also runs the gate's `mypy-tools` suite, one under `test/fw/` `mypy-fw`, and `pyproject.toml` (the mypy config) both, each run with the command `gate.py` defines for it, because the merge queue runs them; a change under `patch/` or to a top-level file of `tools/` (or to `docs/rebasing/sitenotes.py`) also plans `test/stock_sites.py`, which runs `sitenotes.py --check` (12 s, no build, needs the stock zip: `$Q2_STOCK_ZIP`) so `tools/stock_sites.tsv` cannot go stale unseen; a `tools/` module (not `tools/ci/`) or its `test/unit/test_X.py` also plans `cov:tools/X.py`, `tools/ci/covcheck.py`: the `test/unit` files that import or name the module run under coverage and the module alone is held to the post tier's `fail_under` (about a second for `q2flash.py`; the twelve files that name `build.py` take about a minute), so a branch that drops a module under the floor is rejected before it lands, not `POST_RED` after; a change under `patch/` also plans the [smoke test](#smoke-test), which `--run` skips unless given `--smoke` (optional for a worker: the queue runs it on the tip after landing); `tools/iroh.py` and `tools/uac1.py`, whose only output is a pinned file the build puts in the image (`IMAGE_INPUTS`), run `test/build.py` and not the payload's suites; a file under `tools/uac1_module/` runs `test_uac1.py` (the pin over that folder), `test_iap_tools.py`, `test/build.py` (the build refuses an unpinned change) and `test/uac1_bind.py` and `test/uac1_isoc.py` (skipped with their reason: they need a built module), one under `tools/iap_probe/` `test_iap_tools.py` and `test/iap_probe.py` (`TOOL_DIRS`), and a file in any other `tools/` folder but `tools/ci/` runs everything; `remote/iroh-sidecar/` runs `test_iroh.py` and `test/build.py`, `remote/coda-rc.proto` `test_coda_rc.py` and `test_coda_rc_lib.py` (`REMOTE`); a source a suite outside `test/fw` and `test/patch.py` builds, runs or reads plans that suite (`SUITE_SOURCES`, patterns rather than names, so a file split out of one is covered, and for a suite that compiles its sources every header and `.inc` they include, followed by `included`): `patch/coda_rc*`, `remote/coda-rc.proto`, `tools/coda_rc_client.py` and `tools/ci/emu_pool.py` plan `test/coda_rc_e2e.py`, a `patch/q2_iap*`, `patch/iap_*` or `patch/iap2*` source or `patch/q2car.sh` `test/iap_probe.py`, `patch/peq*` and the other sources `test/peq.py` builds (`hash.c`, `games.c`, `video.c`, `radio.c`, `spotify.c`, `netupdate.c`, `onlinematch.c`, `tidal.c`, `scrobble.c`) and OLED's theme plan it, and `patch/peq.c` plans `test/player/run.py`; a payload change also plans `test/playback.py` and `test/headset_io.py` (`PAYLOAD_SUITES`), which run the build's payload as `test/patch.py` does; `tools/ci/test_ci.py` fails on a source a suite's code names that plans no suite of it (`test_every_source_a_suite_names_in_its_code_plans_it`); a file no rule knows runs everything: the gate's merge tier, every suite a rule here plans (`gate.PLANNED`: `test/coverflow.py`, `test/player/run.py`, `test/stock_sites.py`, the CI tools' own tests, `test/subsonic_contract.py`, `test/subsonic_seam.py`, `test/iap_probe.py` and `test/coda_rc_e2e.py`) and `smoke`. An integration branch (`release/*`, `integ/*`, `main`) runs everything when `affected.py` is given neither `--base` nor `--plan-json` (a bare run checked out on one plans it all); with either, it runs that diff's plan or the plan given, as an integrator's run after one merge does; the user's integrator runs it on an `integ/*` branch once, on its last merge (`--all`, [orchestration: Integration branches](orchestration.md#integration-branches)). Of the 47 branches merged on 2026-11-16, 41 touched the payload: for most branches "what it needs" is the whole MIPS suite, which is why that suite's cost decides everything else here.
- **How `--run` runs a plan:** through `gate.run`, with the suites `gate.py --plan-json` would give the same plan (`gate.suites_for`), so a worker runs exactly what a merge batch runs. They start at once as memory allows (the [gate](#gate)'s rule: the longest first, each only while `MemAvailable` stays 4 GB above its estimate), the heavy ones under `q2-heavy`, each to its own log under `~/.cache/q2-gate/<worktree>-affected-<time>/`; a failed suite's last 30 lines are printed, then a table of each suite's result (`ok`, `FAILED`, `flaky`, `cached`) and seconds. A suite that fails is run once more, alone: one that then passes is `flaky`, counted as passed and appended to `~/.cache/q2-queue/flakes.jsonl`, and one that fails again fails the run (`--no-retry`: no second run). A suite that passed on this exact tree (a clean worktree, the same command, a build made with the same `rebuild.py` options) is `cached` and not run, its pass shared with `gate.py` (`--no-cache`: run it). Without a build only the suites that need none run, each other one named with `needs a build`. The exit status is 1 when any suite failed. An everything plan (`--all`) is the merge tier and `gate.PLANNED`, about 31 minutes one after another by the gate's timing table (`gate.SECONDS`) and about an hour as integration runs took when `--run` ran them one at a time (to 2026-11-20); side by side it takes as long as its longest suite, as the rest together fit in that time: `test/player/run.py` (about 13 minutes in an integration run) or `test/iap_probe.py` (9:02 alone on 2026-11-22, 77 MB: q2-iap built for this machine and run as `q2car.sh` runs it, no build needed). `test/coda_rc_e2e.py` (`--pool BUILD`: it leases a pooled emulator, so it waits when none is free) took 17 s on a pooled emulator the same day. Both are in it so the last full run before an image is driven in the car cannot skip the car's two suites; `test/coda_rc_iroh_e2e.py` needs n0's public relay and stays by hand.
- **The MIPS suite runs serially.** `test/patch.py BUILD` in one process takes 4:39 on one core and about 1.2 GB (measured on an idle machine, 2026-11-16, 2,603 scenarios). It is one script whose later tests use the state the earlier ones left, so a parallel run has to replay most of the suite in every part: eight shards took 10:26 and 5.2 GB on the same machine. The gate, the queue and `affected.py --run` all call `test/patch.py` directly, under `q2-heavy`. Several serial runs fit side by side (a core and 1.2 GB each), which is what lets every worker check its own branch while a batch runs.
- **Shards** (`patch_shards.py`) are for part of the suite only: `--lines A:B` runs the statements on those joined-suite lines after their slice, every def, class and import before them and each earlier statement that binds or changes a name the range reads (by name, from the source; a call counts as changing what it is passed). `python3 test/suite_source.py LINE` names the file and line of a joined line. A slice can miss state that is not a name (a file, a C library's memory): there is a known gap at `07_messages_lyrics.py:938`, where any range past joined line 7674 fails in replay. So a `--lines` result is a quick look while writing a test, never the check a branch is queued on, and a full sharded run is refused by the command guard ([orchestration: Rules](orchestration.md#rules)). `--verify` compares a sharded run's traces with a serial run's, byte for byte, and is how a fix to the slicer is proved.
- **Why a replayed failure stops a shard:** a failed `Machine.call` can leave unicorn about to translate garbage, and unicorn 2.1.4 then crashes in `temp_load` (`tcg_gen_code`, a NULL read) on the next call. Reproduced on 2026-11-16: release/p31 at `531adece` fails at line 11179, and running on past it (a slice's replay, or a keep-going survey) crashed at line 12812 every time; stopping at the failure ends the crash.
- **test/fw on workers** (`fw.py`): the library is built once and handed to `pytest -n N --dist loadfile` through `Q2_FW_LIBRARY`; each test loads its own copy and the C's fixed addresses are per process, so workers share nothing; within a process conftest.py zeroes those addresses before every test (`stock_memory`), so a file's result does not depend on which files a worker ran before it. N comes from memory, at most 6, never `-n auto`: 9,052 tests in 49 s. Needs `pip install pytest-xdist`; without it the run is serial. Under the sanitizers (`--asan`) a process's memory grows with every test it has run (two workers reached 9.4 GB and were killed on an idle machine), so the files run in eight groups, each a pytest process of its own under `q2-heavy`, three at a time: 3.7 GB at the peak, 1:53. Feature branches run it plain; ASan and coverage belong to the gate's post tier.
- **Builds** (`rebuild.py`): one place per worktree, `~/.cache/q2-builds/<worktree>[-dev]/`, holding this build and the one before it and a `cur` link; nothing is built when the sources (`source_sha256`, and `remote/iroh-sidecar`'s `crate_sha256`, which `--build-iroh` compiles and the pinned path checks) and options match the last build. It puts ccache in front of clang and cc (`/usr/lib/ccache`, `CCACHE_BASEDIR=$HOME`, `CCACHE_NOHASHDIR=1`: the payload is built without `-g`, so worktrees share objects safely), sets `Q2_BUILD_CACHE` for `memo` in `tools/build.py` (the font work, keyed by `tools/build.py`'s text, fontTools' version and the inputs), hardlinks the stock files every build writes unchanged to one copy, and drops `root.pseudo`, the build's 108 MB scratch. `tools/release.py` runs `tools/build.py` without any of this, so its two reproducibility builds compute everything.
- **`q2-heavy`** (`tools/ci/q2-heavy`, installed as `~/.local/bin/q2-heavy`): runs a heavy job in one of 10 slots (`Q2_HEAVY_SLOTS`) when `MemAvailable` is 5 GB or more, memory and io pressure are low, the Windows drive (`/mnt/c`, where WSL's disk lives) has 25 GB free and the battery allows (on battery: one job under 30%, none under 15%); else it waits and says why. Under 10 GB on `/mnt/c` it refuses (exit 75) and pauses a running job. A start holds a lock for 5 s (`Q2_HEAVY_RAMP`), so the next job's memory check sees this one's; the job itself does not inherit that lock, or no other job could start until it ended. Each job runs in a systemd scope of its own, `q2h-<pid>.scope`, with `MemoryMax=3G` (8G under ASan; `Q2_HEAVY_MEM` sets it) and with `tools/ci/nodump.c` preloaded, so a crash leaves no core dump (the flag it sets is non-dumpable, so a job's `bwrap --unshare-user` cannot write its uid map and a ptrace target must set itself dumpable: `test/thirdparty.py`, `test/player/fakedemo.py` start bwrap without the preload and `test/remote.py`'s target calls `PR_SET_DUMPABLE`): WSL pipes cores to the Windows drive and a pipe ignores `ulimit -c`, and a 33 GB core filled C: on 2026-11-16. A job has a class, `Q2_HEAVY_CLASS`: `branch` (the default, a worker's own run) or `queue` (the merge queue's). At most six branch jobs run at once on the charger with 8 GB available, four otherwise (`Q2_HEAVY_BRANCH_SLOTS` sets the number; measured 2026-11-22: branch jobs peaked at 0.1 to 1.1 GB, fw alone near its 3 GB cap, four slots left a full run 80 job-minutes waiting, and eight drove CPU pressure to 37% and wall-clock tests red), and no job starts while CPU pressure (some avg10) is 30% or more and each gets a fifth of the queue's CPU weight, so a batch keeps its speed whatever the workers start. A job has a deadline, `Q2_HEAVY_MAX_S` (1,800 s): its scope is stopped then and `q2-heavy` exits 143. And it has a record while it runs, `~/.cache/q2-heavy/jobs/<pid>` (class, worktree, command, start, deadline, scope), which `q2 status` lists and `q2 stop-all` uses to stop it. Install it by rename, never by copying over it: bash reads a running script as it goes, and a job running it then ends with a wrong exit status (`install -m 755 tools/ci/q2-heavy ~/.local/bin/q2-heavy.new && mv ~/.local/bin/q2-heavy.new ~/.local/bin/q2-heavy`).
- **`q2-wait`** (`tools/ci/q2-wait`): `q2-wait --pid PID --timeout S` returns when the process is gone, `q2-wait --log FILE --match REGEX [--fail REGEX] --timeout S` when a whole line of the log matches; `--timeout` is required and at most an hour, and running out is exit 124. It replaces every hand-written wait loop: `until ! pgrep -f PATTERN` matches the waiting shell's own command line and never ends, and 26 such shells were found on 2026-11-16, the oldest four hours old.
- **Merges:** `.gitattributes` merges `docs/changelog.md` as a union, so two branches' bullets at the top of Unreleased no longer conflict (a bullet both reworded comes out twice: keep one). Tables such as `docs/source-map.md` stay normal merges: their rows are edited as often as added, and a union would keep stale copies. `git rerere` is on in this checkout (`rerere.enabled`, `rerere.autoupdate`), so a conflict resolved once is resolved the same way when it comes back.

### Merge batch

`tools/ci/merge_batch.py` is how branches reach the trunk; the [merge queue](#merge-queue) runs it, nobody else does. A worker whose branch is done merges the trunk into it, runs its own `affected.py --run "$B"` and, when that is green, queues the branch with `python3 tools/ci/merge_batch.py --mark-ready` in its worktree. `--mark-ready` is refused with uncommitted changes, for an integration branch, for a commit the trunk already holds, and for a branch that would not merge: it tries the merge in memory (`git merge-tree`) and names the conflicted files, and the worker, who wrote the code, merges the trunk in and resolves them. It appends the branch and its commit to `~/.cache/q2-merge-train/ready.txt`; the batch merges that commit, so the worker can go on committing, and later commits need another `--mark-ready`. `--fixes-tip` marks a branch that repairs a failure the trunk itself has.

A batch (`merge_batch.py --from-ready`, in the trunk's clean worktree, with `~/repos/q2-pod/.venv/bin/python`) takes and empties the ready list and:

1. merges every branch (`--no-ff`, rerere as above) onto the trunk's tip, in a worktree of its own (`~/.cache/q2-merge-train/wt/<trunk>-L0`, kept between runs); a branch that conflicts, or is in the tip already, is skipped and reported, and the rest go on;
2. builds once (`rebuild.py`, that worktree's reused build) and runs, once, what `affected.py` says the batch's whole diff needs, through [`gate.py`](#gate): the merge tier and the plan's own `other` suites when the plan runs `unit`, `fw` and `patch` whole;
3. green: fast-forwards the trunk to the tested commit (merge commits only; nothing is rebased) and lists what landed;
4. red, every failed suite a crash (its process died, twice: see the gate): lands nothing and blames no branch, since the fault is the harness or the machine and a bisection would pin it on whichever branch the next crash fell on;
5. red otherwise: runs the failing suites on the tip alone, and stops there, landing nothing, when the tip fails them too (every branch would look guilty). Otherwise it bisects. The branches are split in halves and only the failing suites run on each half, on top of what has passed so far, with the tests the batch's run planned for them (joined with the half's own plan), not only those the half's changes map to: otherwise a branch that breaks a test only a later branch's plan reaches would pass its level and the later branch would be blamed (batch `20261116-232912` rejected `feat/p32-streaming` for `feat/row-press`'s failure). It runs in one worktree and build per level (`-L1`, `-L2`, ...). A half whose sibling passed is known to fail without a test, down to a single branch, which is always tested: a flaky failure cannot convict the last branch. Each culprit is kept as `train/failed/<branch>` and reported with the suite, its log and the failing tests; the remainder, already a tested commit, runs again in full (what its own diff needs) and lands when that is green. When no half fails on its own, nothing lands and the summary says so.

One culprit in ten costs six or seven runs of the failing suites, the tip's included (counted on a fake repository in `test_ci.py`). `--dry-run` merges in memory and prints the conflicts and the plan, in a second or so; with `--onto BRANCH` it runs from any worktree. `--result FILE` writes what happened as JSON (landed, culprits with their suites and first failures, skipped with why, whether the tip is red, which suites crashed), which is what the queue reads. Logs and `summary.txt`: `~/.cache/q2-merge-train/<time>/`. The exit status is 0 when everything landed, 1 when a branch was left out, and 2 when nothing could land.

### Merge queue

`tools/ci/merge_queue.py run` is the service that integrates: a loop with no agent in it. It takes everything on the ready list (one branch or fifteen; it never waits to fill a batch), runs a [merge batch](#merge-batch) on it in the trunk's worktree, and writes each outcome as one line to `~/.cache/q2-queue/events.log`: `READY`, `BATCH`, `LANDED`, `REJECTED` (with the suite, the first failure and the log), `CONFLICT`, `SKIPPED`, `REQUEUED`, `TIP_RED`, `INFRA`, `POST_OK`, `POST_RED`, `PUSHED`, `QUEUE_STOPPED`. Its state is `~/.cache/q2-queue/status.json`; `merge_queue.py status` and `q2 status` print it. Branches that become ready during a batch go in the next one, so a branch waits one batch at most before its own.

- **The trunk** is the one integration branch: `$Q2_TRUNK`, else the first line of `~/.config/q2/trunk`, else `release/p31` (`tools/ci/q2ci.py`). `affected.py` compares against it and `--mark-ready` checks against it.
- **Only the queue moves the trunk.** `tools/ci/hooks/reference-transaction`, installed as the shared repository's hook, refuses to create, move or delete `refs/heads/release/*` or `refs/heads/main` for any process without `Q2_QUEUE=1`, which the queue sets for its batches: a commit, merge, reset or `branch -f` on the trunk from any worktree fails before anything changes. So the tip is a commit the gate passed, always, and "a failure that was already on the release branch" has one way left to happen, a flaky test. `Q2_TRUNK_ADMIN=1` is the user's override for cutting a new trunk by hand.
- **A red tip** (the batch failed and so did the tip alone): the queue says `TIP_RED`, puts the batch's branches back and from then takes only branches queued with `--fixes-tip`, until one lands. Nothing else is tested against a broken base in the meantime.
- **Crashes:** a batch that only crashed is put back (`INFRA`, `REQUEUED`); after two in a row the queue stops itself (`QUEUE_STOPPED`, the `STOP` file), because a third would crash too. `merge_queue.py resume` clears a stop, the crash count and a red tip's hold, on a running service too: it leaves a `RESUME` flag file in `~/.cache/q2-queue/`, the loop takes it at the top of its next turn, drops the same holds from memory and logs `RESUMED`. No stop and start.
- **An undecided failure** (the batch failed, no half failed alone: a flaky test) is tried once more, then rejected.
- **The post tier** runs on the tip when nothing is ready and the tip has not had it: the sanitizers, coverage, the [smoke test](#smoke-test) and the [leak hunt](#leak-hunt). `POST_RED` names a commit that has already landed; it is fixed by the next branch, as any bug. A failed smoke test (exit 1: the build crashed or lost its way on an emulator) also turns the tip red (`TIP_RED smoke`), with the hold above, since every user of the trunk would hit it; the smoke test's exit 3 (no emulator came free) holds nothing. A leak found (the leak hunt's exit 1) is `POST_RED leak-hunt` and nothing more: it never holds the tip, and it is never in a merge batch.
- **Stopping:** `q2 stop-all --yes` writes the `STOP` file; the queue ends its running batch (and everything the batch started) within seconds, puts the batch's branches back on the ready list and idles until `resume`.

### Gate

`python3 tools/ci/gate.py`, with `~/repos/q2-pod/.venv/bin/python` (it has pytest-xdist, coverage and mypy), is one `--dev` build (`rebuild.py`; other options after `--`), then every suite at once, each to its own log under `~/.cache/q2-gate/<worktree>-<time>/`, and a table of each suite's exit status and time. The suites come in two tiers. **merge**, what a batch must pass before it lands: `patch` (`test/patch.py`, serially), `unit`, `fw`, `test/playback.py`, `test/build.py --build`, `test/peq.py`, `test/headset_io.py`, `mypy-tools` and `mypy-fw`. **planned** (`gate.PLANNED`), what a rule of `affected.py` plans for a change no merge suite covers: `test/coverflow.py`, `test/stock_sites.py` (`sitenotes.py --check`, 12 s), `test/player/run.py` (about 4.5 minutes alone on 2026-11-22: its tests and fixtures eight at a time, each mostly waiting on a player running in real time, then the sixteen that bound real-time behaviour or read the host's /tmp one at a time; 10 minutes when everything ran one after another; not in the merge tier), `tools/ci/test_ci.py` and `tools/ci/test_orch.py`; they run when a plan names them, and a plan that runs everything names them all. A `test/X.py` a plan names runs as `gate.SCRIPTS` says (the argv its parser takes: BUILD, qemu (a static one for `test/thirdparty.py`, whose chroot holds no host libraries: `$Q2_QEMU_STATIC`, `qemu-mipsel-static`, or a pool copy's), the stock rootfs's module files or nothing), or is skipped with a printed reason when it cannot run there. A plan that runs `unit`, `fw` and `patch` whole gets the merge tier and its own `other` suites beside it (a planned suite its changes need, a `test/X.py` the branch changed): on 2026-11-18 such a plan (`d553a94b`) got the tier alone, which dropped the `test/coverflow.py` it broke, and the trunk was red unseen until the next Coverflow change. **post**, what runs on the trunk after a landing: `fw-asan`, `unit-cov` (`test/unit` under coverage, then `coverage report` against the floor) and `smoke` ([smoke test](#smoke-test)) and `leak-hunt` ([leak hunt](#leak-hunt)). A plan's `smoke` (`gate.OPTIONAL`) is left out of a merge batch's run; `--only smoke` runs it. `--tier merge` or `--tier post` runs one; with no plan and no tier the gate runs all three (merge, planned and post), which is a release's gate. The suites that need no build start beside the build, the longest first. A suite starts only when `MemAvailable`, less the estimate of each suite started in the last 30 s, stays 4 GB or more after its own estimate (`MEM_GB`); else it waits for one to finish. Heavy suites run under `q2-heavy`. `--plan-json` runs what an `affected.py` plan names (how `merge_batch.py` uses it), and `--only NAME,...` keeps some of it. The exit status is nonzero when any suite failed. The fastest it can be is the build plus the serial MIPS suite, about five and a half minutes.

- **A pass is recorded, per tree.** A suite that passed is written to `~/.cache/q2-verified/` under the tree's hash (`git rev-parse HEAD^{tree}`), the suite's command and the build's options, and a later gate on the same tree reports it `cached` and does not run it: a release's gate after a batch on the same commit costs only the post tier, and a batch of one branch that already holds the trunk's tip reuses the worker's own gate run. Nothing is recorded or reused when the worktree holds anything git does not (a changed file, an untracked one outside the ignores), and a pass that followed a failure is never recorded. `--no-cache` runs everything.
- **A failed suite is run once more, alone** (`--no-retry`: not), with nothing started beside it. A pass then is `flaky`: the gate passes, the table says so, and a line goes to `~/.cache/q2-queue/flakes.jsonl`. A failure carries its `kind`: `crash` when the process died of a signal (a Unicorn segfault, a memory limit's kill, a deadline's) or its log shows one, else `fail`.
- **Known failures:** `test/known_failures.tsv` lists pytest tests that fail on the trunk and whose fix is owed (suite `unit` or `fw`, the test's id, a date, an owner, a reason, tab-separated). The gate deselects them in both runs of that suite, so one known failure blocks nobody else's merge, until the date; a line past its date, or one that names a suite that cannot skip a test, fails the gate as the suite `known-failures`. `test/patch.py` cannot be listed: a later test needs the state an earlier one left, and Unicorn can crash after a failed call, so a failure there is fixed (a red tip, above), not skipped.

### Merge train

`python3 tools/ci/merge_train.py BRANCH...` merges each branch in turn, testing after each, and stops at a conflict with the merge left in progress. It predates the queue and is kept for one case: the user integrating by hand, with `Q2_TRUNK_ADMIN=1`, while the queue is stopped. A failed merge is kept as `train/failed/<branch>` and the integration branch goes back to the last merge that passed. `--dry-run` prints what each merge would test. Logs: `~/.cache/q2-merge-train/<time>/`. An `integ/*` branch is not assembled with it: its merges get a build check each and the suites run once, on the last ([orchestration: Integration branches](orchestration.md#integration-branches)).

### Emulator pool

`python3 tools/ci/emu_pool.py get BUILD` leases one of four shared emulator copies, `~/q2-emu-pool1` to `~/q2-emu-pool4` (port 2401 up), boots BUILD on it and prints how to drive it (`~/q2-emu-pool2/q2emu shot out.png`, `key centre`, `wheel 3`, `tap X Y`). `put SLOT` gives it back; a lease lasts two hours unless renewed (`renew SLOT`), and an expired one is stopped for the next agent. Asking again for the same build under the same name reuses the running emulator. When all four are leased, `get` waits. The copies are made from `~/q2-emu-server`'s scripts and serial record; nothing there is changed. Use the pool instead of cloning a copy of your own: 14 emulators and builds at once took the machine down on 2026-11-16.

**The card.** Every lease starts with the card (`state/mmc`, the guest's `/mnt/mmc`) as the fixture, `~/.cache/q2-emu-pool/card` (`Q2_EMU_CARD`): `get` stops the copy's emulator, removes whatever the last lease left on the card (a cache file, a `.subsonic` folder, a switched file, a changed config line) and hardlinks the fixture's tree in, so the disk use stays flat. A copy on another filesystem than the fixture gets the files copied instead (the card is about 6 MB): on GRAYTHINKPAD `~/q2-emu-pool1` to `4` are symlinks onto the scratch disk, `/mnt/wsl/q2scratch`, while `~/.cache/q2-emu-pool` stays on `/`, and a hardlink across the two failed every `get` with "Invalid cross-device link" (2026-11-20). `emu_pool.py fixture DIR` (re)makes the fixture as hardlinks of DIR's files, read-only, so a lease that writes a fixture file in place fails instead of changing every card; a worker that wants a different card edits it by replacing files, and the next lease puts it back. Stock does not rescan its library (`state/data/database.db`) at boot, so a library left by another card lists songs this card does not hold, and Centre on one says File Not Found and opens no Now Playing (2026-11-18, read at first as a firmware regression). So the fixture has a library too: `emu_pool.py fixture DIR --library DB` keeps DB (a `database.db` from Scan Music Now on a lease of DIR) as `~/.cache/q2-emu-pool/card.db`, and `get` copies it over the copy's `database.db` (a copy, as stock writes it); a new fixture without `--library` drops the old one, and the copy's `database.db` is then left as it was. A lease reused (same name, same build, emulator running) and one already reserved keep their card, library and data. With no card fixture `get` says so and leases nothing. `smoke.py` exits 3 with "the card on slot N has no songs" when the card it was given holds no audio file, apart from its "no pool emulator came free".

**The settings.** The rest of `state/data` (`/mnt/data`) is reset from a data fixture, `~/.cache/q2-emu-pool/data` (`Q2_EMU_DATA`), the same way, at a fresh lease only: a scripted tour left Light Mode, Smart Awake and Song Length changed in slot 1's `config.ini` and later workers' runs started from them (2026-11-18). `emu_pool.py fixture --data DDIR` (alone, or beside the card's `DIR`) hardlinks DDIR's top-level files read-only (not `database.db`: that is the library's), and `get` removes the per-run files (`DATA_PER_RUN`: `memoryfile`, `q2-state`, `q2-stall`, `q2-cf-trace`, `q2-library-scope`, `peq-active`, `ringnav-*`: Memory Playback, the state record, the queue, play counts, ratings, orders and speeds) and copies the fixture's files over the copy's. They are copied, not linked, because stock writes `config.ini` in place and a linked one would change the fixture for every lease. The settings are `config.ini` alone; kept are `wpa_supplicant.conf` and `q2-defaults` (boot and Wi-Fi), `q2-battery`, `userequalizer`, `coda-rc` (the pool's Car Remote stand-in) and the logs. Seed DDIR from a clean default, never from a slot: the build's `config.ini` (the shipped default, `<build>/config.ini`) with `BLUETOOTH=0` (`mkdir DDIR; cp BUILD/config.ini DDIR/`; the shipped file already has it off, and the smoke test turns it off anyway). Without a data fixture `state/data` is left as it was.

A lease made with `get --reserve`, or marked later with `emu_pool.py reserve SLOT` (the user's own rig, slot 2), is never reclaimed when it expires and never handed to another name; `status` shows it RESERVED, and only `put` or `reserve SLOT --off` frees it.

The emulator has no Bluetooth controller, and the pool's copies keep `BLUETOOTH=0` in `config.ini`, so stock never starts the stack. A copy with `BLUETOOTH=1` fails it at every boot, which on a Q2 opens the Bluetooth Stopped page; the firmware shows no such page and never restarts when `/lib/libq2emu.so`, the emulator's shim, exists ([internals](internals.md#bluetooth-boot-reconnect)). The boot card the smoke test confirms is No Temperature Sensor (the emulator has no PMIC), not Bluetooth. demo names that card in `/tmp/q2guard.ack` a few milliseconds after the card is on screen, so the boot step looks again for up to a second (`ANSWER_S`) before it calls an unnamed card a failure: a look that fell in that gap was the smoke test's first-run flake of 2026-11-18. Its OK then waits for stock's boot-key countdown to end (`boot_keys`, `BOOTKEY_FLAG`: `g_ingore_bootkey_flag`, which stock sets at Home and counts down from about 5 a second apart, dropping each Centre release meanwhile as the power key's; `patch/nav/input.c` drops it too). The card usually comes about 9 s after Home, past it; when it came inside it (4 boots of 108 on 2026-11-23, each within 5 s of Home, mostly a build's first boot on a copy), the OK was dropped and the boot failed with "No Temperature Sensor did not close on OK". Set to 3 by hand under a card at rest, the countdown made an OK sent at once miss 3 times of 3, and one sent after it ended close the card 3 times of 3.

Each copy's Car Remote daemon listens on its own TCP port, 7700 plus the slot (`~/q2-emu-pool2`'s on 7702), not the Q2's 7720, so two copies with Car Remote on never fight over one port. `emu_pool.py` (`fit`) gives each copy's `q2emu` its `Q2EMU_CODA_PORT`, and its `run.sh` binds a stand-in over `/usr/bin/coda-rc` that runs the build's own daemon with `--port`; the firmware is unchanged. A phone or Android Auto rig that reaches the Q2 at `127.0.0.1:7720` through `adb reverse` points at a slot with `adb reverse tcp:7720 tcp:7702` (the aa-dhu rig on slot 2), or sets the app's TCP address to `127.0.0.1:7702` instead. A copy made before this gets it at its next `get`.

### Smoke test

`python3 tools/ci/smoke.py BUILD` boots the build on a [pooled emulator](#emulator-pool) and walks it as a user would, in about a minute and a half: Home > Library > Songs > Center (Now Playing opens) and Return; Cover Flow, once its art is built, > Center on an album (its tracks) > Center on a track (Now Playing); Settings > General, Playback, Display and Battery, each opened and closed; Control Center pulled down and closed with Return; Search, where the letter strip types "AU" and results show, closed with a held Return. It is the one suite that runs the real `demo` with Shanling's AWTK: `test/fw` links the payload against stand-ins for stock's functions and `test/patch.py` runs it under Unicorn with no window manager, and on 2026-11-17 a NULL read on every Now Playing open from a list passed both for about an hour and a half (the fw stand-in for `widget_get_prop_str` returned its default where stock returns NULL).

- **A streamed song.** With the pinned Subsonic zip and `~/repos/q2-subsonic` here, the copy's card also gets the app (the zip's MIPS program), signed in to `q2-fakesonic` (test/subsonic_seam.py's pin) running on this machine's RFC 1918 address at a port the kernel picks, which the emulator reaches as it shares this machine's network; its songs are titled `0 Seam ...` so they sort first, and each is the card fixture's first FLAC (`-audio`), as the fake's own bytes are no audio the player decodes (it skipped each in about 2 s). After the boot the walk waits for the app's catalogue to be imported, and Library > Songs > Center then plays a server song: the step passes once `/tmp/coda-rc.now` (Car Remote's Now Playing, CARREMOTE=1 for the lease) names a song under `/mnt/mmc/.subsonic/`, playing and not loading, and its position moves on. Without the zip, the repository or such an address it says why and walks on with a card song; `--no-stream` leaves it out.
- **A step passes** when the window it should open is on top of demo's window manager, read from demo's memory through `/proc/PID/mem` at V1.36's addresses (`smoke.py` `windows`; the status bar and a toast are looked past), or, for a step that stays in one window (Settings' list, typed text), when the screen changes in the part of it that matters (Home's art slides on its own). Cover Flow's steps read what its page shows from its widget tree (`window_tree`, `coverflow_screen`: the carousel's `slide_menu` shown is the covers, hidden under the text list an album's tracks, absent while the albums load): the walk waits up to `ART_S` (60 s) for the covers before its Center, and then for the tracks. Every lease starts with no art cached, which builds behind the covers once they show ([internals: Coverflow](internals.md#coverflow)), so the covers come before their art. After each input it waits for the screen to come to rest: each input device is its own FIFO, so a key sent straight after a turn can land before the turn's last samples.
- **Any step fails at once** when demo's process has gone or been replaced (found as `q2emu` finds it, by the `bwrap` that binds the copy's `rootfs`; `q2emu` resolves its folder with `readlink -f`, so `smoke.py` and `q2live.py` resolve `~/q2-emu-poolK` too: matching the symlink's path found no demo on the scratch disk's copies, 2026-11-20): the screen and the run's part of `demo.log` (where qemu reports the signal) go to `--logs` (default `~/.cache/q2-smoke/<time>/`). `--shots DIR` saves the screen as each step starts. The run has a hard deadline of 170 s after the lease.
- **The emulator** is leased as `smoke-PID` for 15 minutes and never on slot 2 (`emu_pool.get(avoid=)`), with `BLUETOOTH=0` written into the copy's `config.ini` before the boot (`prepare=`) and the file put back after, and the lease returned whatever happens, a signal included. A lease is waited for up to `--wait` seconds (600); none in time is exit 3, and so is a card with no songs (said as such).
- **Exit status:** 0 passed, 1 failed (the step and why on the last line), 3 could not run. The queue's post tier treats 1 as a red tip and 3 as no verdict ([Merge queue](#merge-queue)).
- **Proved on the crash it was written for:** a build of `d8bafa8c` (feat/p32-motion landed, fix/coverflow-tracks-crash not yet) fails at `Songs > Center: Now Playing: demo crashed`, `Segmentation fault`, 20 s in; the trunk with the fix (`08e1121e`) passes every step in 92 s, twice in a row.

### Leak hunt

`python3 tools/ci/leak_hunt.py BUILD` asks what [the smoke test](#smoke-test) does not: does the UI give back what it takes. It boots the build on a [pooled emulator](#emulator-pool), runs one fixed tour five times (`LOOPS`; `--loops N`), and reads demo's state on Home after each run: the window manager's windows, every widget under them, the live timers and idle callbacks (read from demo's memory through `/proc/PID/mem`, as `smoke.py` reads the window stack) and demo's resident set. The tour is Library > Songs > Center (Now Playing) > Return, Control Center pulled down and closed, and Search typed into and left with a held Return: about 34 s a run on a pooled emulator. The first run is a warm-up, so lazy caches and first-use allocations settle; the sample after it is the baseline.

- **A count is a leak** (windows, widgets, timers) when it ended above the baseline and rose in at least two loops: a leak adds every time, a cache that fills once rises once. **Memory is a leak** when it ended more than `RSS_TOL_KB` (12 MB) above the baseline. `verdict` in `leak_hunt.py` decides, from the samples alone, and each finding names the metric and the first loop it grew in (`timers grew from loop 2: 9 -> 10 -> 11 -> 12`).
- **Measured on 2026-11-18** (a `--dev` build, slot 1): windows 2, widgets 95, timers 9 in every loop; resident set 71,932 to 72,468 to 71,772 kB (within 700 kB); 188 s in all, 16 s of it the boot. A first try with Cover Flow and Settings in the tour cost 67 s a loop and a run of 5.5 minutes, so they are left to the smoke test. A deliberate leak (a timer and 12 widgets added to each sample, standing in for a page that leaks) turned the run red (exit 1, `widgets grew from loop 2: 107 -> 119 -> 131 -> 143`, `timers grew from loop 2: 10 -> 11 -> 12 -> 14`) and the slot went back.
- **Exit status:** 0 no growth, 1 a leak (each named on a `LEAK` line), 3 could not run: no emulator came free in `--wait` seconds, the tour lost its way or demo died (the smoke test is the test for that), or the hard deadline (`DEADLINE`, 240 s after the lease) passed. The lease is returned whatever happens, and never on slot 2.
- **Where it runs:** the post tier, beside `smoke` and under unit-cov's five and a half minutes, so the tier takes no longer. `leak-hunt` is not in the merge tier and a plan never names it: no branch waits for it, and none is blamed for it. A leak is `POST_RED leak-hunt` and a backlog item, never `TIP_RED` (`merge_queue.py` `TIP_SUITES` holds `smoke` alone). A running queue only runs it after a restart of `q2-queue.service`; `gate.py --tier post --only leak-hunt` runs it by hand.

### Live reload

`python3 tools/ci/q2live.py` in a worktree: one build, a pooled emulator in fast boot, then on every save under `patch/` the screen at the printed URL shows the change on the page you were on. It rebuilds demo alone (`Q2_DEMO_ONLY` in `tools/build.py`: no fonts, art, rootfs or `update.tar`), with the base build's dev number pinned (`Q2_DEV_NUMBER`) so `stock.h` stays the same and ccache recompiles only what changed; copies it over the emulator's unpacked rootfs; restarts only the sandbox (the viewer, and the browser tab, keep running); and replays the route back to the page. Drive the emulator through `q2live.py do key centre`, `do wheel 3` and so on, and each step joins the route; `q2live.py route` shows it, `route 'wheel 4;key centre'` sets it, `route clear` empties it. A change under `assets/`, `tools/` or `player/` takes the whole build and a reboot. `q2live.py stop` gives the emulator back to the pool.

Measured on release/p31 (2026-11-16), a one-line change to a title in `patch/crossfade.c`, six route steps deep:

| Step                              | Before: build, reboot, navigate                                                                               | `q2live.py`                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Build                             | 35.5 s (compile and link 10.9 s, demo patch 0.9 s, fonts, art and rootfs 14.1 s, mksquashfs 4.6 s, tar 1.7 s) | 2.0 s (demo alone, ccache warm; 14 s the first time) |
| Unpack and boot to a still screen | 7.5 s fresh unpack, 10.3 s normal boot                                                                        | 8.0 s fast boot from the unpacked rootfs             |
| Back to the page                  | by hand                                                                                                       | 7.5 s replayed (6 steps)                             |
| Save to screen                    | about 46 s plus finding the page again                                                                        | 17.8 s, on the page                                  |

The boot is most of what is left: demo under QEMU takes about 7 s to draw Home. The route's replay starts with a wheel tick down and up, as demo's first wheel event after a boot moves nothing.

## Security scan

```sh
python3 tools/scan.py                       # all four scans, firmware from /tmp/q2-dev
python3 tools/scan.py --only code,secrets   # a subset: code, secrets, deps, firmware
python3 tools/scan.py --build /tmp/q2-build # another build's rootfs
```

`tools/scan.py` runs Semgrep over `patch/` and `tools/` (the project's rules in `.semgrep/q2pod.yml` and Semgrep's C and Python packs), gitleaks over the git history, osv-scanner over the requirements files (not the copies in generated trees such as `mutants/`, `scan-out/` and `.venv`; `GENERATED` in the script), and syft and grype over a build's root filesystem. syft names few of the rootfs's components, as buildroot keeps no package database, so `PROBES` in the script finds the rest (OpenSSL, curl, BlueZ, wpa_supplicant and others) by their version strings and grype checks them by CPE. It writes `scan-out/SUMMARY.md` and each tool's JSON, and exits 1 when a scan reaches its failing level: a Semgrep error, any secret, any dependency vulnerability, a critical firmware vulnerability. Most firmware findings are in components Shanling built, a build replaces the worst of them ([third-party.md](third-party.md)), and those left (glibc, BlueZ, the kernel) are listed there with why. The scanners are pinned releases, fetched into `~/.cache/q2-scan` on first use and checked against the SHA-256s in the script, the release file's when it is fetched and the executable's then and every time it runs, so a cached scanner that changed stops the scan; Semgrep runs through `uvx`. Reviewed gitleaks findings (documentation placeholders, file hashes) are fingerprinted in `.gitleaksignore`, so a new one still fails.

## Firmware tests

`test/patch.py` runs the real MIPS payload, but it needs a build, so a stock ZIP. `test/fw` runs the firmware's C without one, on every pull request and push to `main` (`.github/workflows/firmware.yml`, with the host suites above that need no build).

`test/fw/host.py` compiles `navigation.c` and `tools/peq.py`'s `UI_SOURCES`, the payload's own files, as they are for the Q2, not through `PEQ_HOST`, and links them into one library the tests load with ctypes. Their `stock.h` is `tools/build.py`'s own (`stock_header`) and `themes.inc` `tools/theme.py`'s, and `peq_platform.h` lays stock's functions out as `tools/peq.py` does, so the color path through `peq.h` is the device's. A stock call, or a libc call with effects outside the process, is a stub: it records the call and returns 0 of its declared type (a float in the float register), or what the test's `fw.mock` returns; `tk_snprintf` and `tk_strcmp` answer as `vsnprintf` and stock's `tk_strcmp` (`strcmp`, a NULL first string -1 and a NULL second 1) unless mocked, and `__errno_location` answers the address of the library's own `fw_errno`, 0 at each load. So a test can't touch the card, the network or this machine. The compiler's own runtime calls (gcov's, the sanitizers', arm64's outline atomics `__aarch64_*`) are linked for real, not stubbed. A test that puts code at a stock address uses conftest's `ret_code`, `returns_code`, `callback_at` (a jump to a ctypes callback) and `call_returning_to`, which write this machine's own instructions, x86-64 or arm64, and `code_at`, which makes arm64's instruction cache see them.

```sh
python3 -m pytest test/fw --basetemp ~/.cache/q2-pytest/fw
Q2_FW_SANITIZE=1 ASAN_OPTIONS=detect_leaks=0:allocator_may_return_null=1 LD_PRELOAD=$(cc -print-file-name=libasan.so) \
    python3 -m pytest test/fw --basetemp ~/.cache/q2-pytest/fw-asan  # AddressSanitizer and UBSan
Q2_FW_COVERAGE=1 python3 -m pytest test/fw  # .gcda files for gcov
Q2_FW_STRICT=1 python3 -m pytest test/fw    # fail a test that reaches a stub tools/ doesn't declare, unmocked
```

- **Where it writes:** each test loads its own copy of the library (about 20 MB, more under ASan), deleted as soon as it's loaded, and a passing test's directory goes (`tmp_path_retention_policy`); a run leaves the session's build, a few MB. pytest's default base is under `/tmp`, which is RAM on many systems, so `--basetemp` on disk is the safer habit. A test that crashes the C (a segfault, a divide by zero) ends the whole run: `-v` names it.
- **Python:** stock's fixed addresses (0x400000-0xc00000) must be free, so the python has to be position-independent. Debian's and Ubuntu's own `/usr/bin/python3` isn't; one built with the toolchain's default `-pie` (Arch's, Fedora's, `actions/setup-python`'s builds) is. conftest stops with a message on one that isn't.
- **Mirrors:** `fw.var` checks a ctypes Structure mirror against the symbol's size, so a C struct that changed fails there instead of reading wrong offsets; `host.offsets(obj, type)` reads a struct's offsets from the debug info where a mirror would be fragile.
- **q2video:** `patch/video.c` is a program of its own on the Q2, so `test/fw/video_host.py` builds it into a library of its own, the same way: the glibc and alsa-lib calls it declares are stubs, and `fw_video_run` runs `main` to its return or its `_exit`. There is no second process: when `fork` answers a pid, the harness first runs `ffmpeg()`'s child's half in place, with that call's own arguments read off its frame where the debug info puts them, so the child's `dup2`s and `execv` reach the stubs too. The unwinder finds that frame (`_Unwind_GetCFA`), so it reads the same on x86-64 and arm64. `test/fw/test_video.py` answers the stubs as a simulated Q2.

- **Fakes answer as stock does, NULLs included.** A fake kinder than stock hides a crash: on 2026-11-17 a NULL read on every Now Playing open passed `test/fw` because the fake `widget_get_prop_str` returned its default where stock returns NULL. `conftest.stock_prop_str` is what stock's answers (a field every widget, window or image answers itself, `text` and any int-valued prop are NULL when read as a string; the default only for a prop never set); `test_nav_lists.Ui`, which most list and window tests share, and the widget fakes of the files with a tree of their own (Cover Flow, hold, library and display pages, the painters, Up Next, the two end-to-end walks) answer through it; a one-line mock for one test's single widget may still answer by hand. `conftest.stock_start_with` is stock's `tk_str_start_with`, false for a NULL, as a never-named widget's name is.
- **Writing one:** `fw.fn('lyrics__lrc_time', restype, *argtypes)` reaches a static as `<file>__<name>`, and `fw.mock` and `fw.calls` take stub names: a stock function's, or `fw_<name>` for libc (`fw_fopen`). Work out the expected answer from what the function is for before running it.
- **`fw.calls` keeps pointers, not what they point at.** A string argument read after the call returned may be the caller's stack, gone: it passes as plain C and fails under ASan as a stack-use-after-return (2026-11-18, `test_battery.py` reading `fw_unlink`'s path). Read such an argument in a `fw.mock` while the call runs. `tools/ci/fw.py --asan` writes each group's ASan and UBSan report to a file as well, and puts it in the group's log with the signal's name if one ended it, since pytest's capture of the test that tripped a sanitizer dies with the process.
- **Song durations:** `python3 -m pytest test/fw/test_durations.py test/fw/test_nav_library_pages.py -k 'durations or long_songs or lengths or cue'` covers the shared cache, Long Songs and Update Local Music's pass; the MIPS worker is `test/patch.py`'s.
- **A known bug** stays as `@pytest.mark.xfail(strict=True, reason='BUG: ...')`: the test fails the job as soon as the bug is fixed, until the mark goes.
- **Limits:** the code runs 64-bit, so `long` and pointers are wider than on the Q2, and stock widgets' layouts don't hold. Code that depends on those stays with `test/patch.py`. The player, `q2player`, is a program of its own, tested by `test/player/run.py`.

## Formatting

```sh
./tools/format.sh          # clang-format 18 over the payload's C, prettier over the Markdown
./tools/format.sh --check  # the same files: changes nothing, exits non-zero on drift
CLANG_FORMAT='uvx --quiet --from clang-format==18.1.8 clang-format' PRETTIER='npx --yes prettier@3' ./tools/format.sh --check
```

The C is `NAVIGATION` (`tools/build.py`) and `UI_SOURCES` (`tools/peq.py`), but the files `UNFORMATTED` beside it names, and the headers `tools/format.sh` lists. `UNFORMATTED` holds upstream's files that were written before the formatter and are kept as upstream writes them, so merges of them stay clean, and the vendored `patch/monocypher/`; a new file is formatted unless it is added there. `CLANG_FORMAT` and `PRETTIER` name the commands where neither is installed. No workflow runs it.

## Type check

`.github/workflows/types.yml` runs [mypy](https://mypy-lang.org) over `tools/`, `test/unit` and `test/fw` on every pull request and push to `main`. Few functions carry annotations, so mypy checks the bodies of unannotated ones too (`check_untyped_defs` in `pyproject.toml`): a misspelt name, a wrong argument count, a `None` used as a value, bytes for a str.

```sh
pip install -r requirements.txt -r test/unit/requirements.txt mypy==2.4.1
mypy tools test/unit
mypy test/fw  # its own run: test/unit has a conftest module too
```

- **`need(value, message)`** in `tools/build.py` is `check` for a search or lookup that can come back `None`: it returns the value or raises the same `ValueError`. mypy can't see through `check(m is not None, ...)`, and `re.search(...)[1]` alone fails.
- **Off on purpose:** `func-returns-value` (the tests' mocks return `list.append`'s `None`) and `var-annotated` (an empty list or dict). A name may take a new type (`allow_redefinition_new`), as in `d = pathlib.Path(d)`.
- **ctypes `_fields_`** is one list, `[*((k, C.c_int) for k in ...), ('x', C.c_void_p)]`: mypy reads lists added together as a list of `object`, which `Structure` refuses.

## Mutation tests

`.github/workflows/tests.yml` runs `test/unit` on every pull request and push to `main`. `.github/workflows/mutation.yml` runs [mutmut](https://github.com/boxed/mutmut) on every function in `tools/`, and on Sundays `test/cmut` over the C ([below](#c)). mutmut breaks a copy of each function in one small way at a time and checks that `test/unit` notices. It uploads every surviving mutant and mutmut's log as `surviving-mutants`.

- **Pull requests:** mutate only the functions they add or change since their base commit (`targets.py --since`), and report the score in the run's summary without failing. `targets.py` asks mutmut's own generator which functions have mutants, so a change to a decorated function (but for a lone `@staticmethod` or `@classmethod`) or to one with nothing to mutate, such as `return self.x`, mutates nothing.
- **Nightly:** mutmut keeps a hash of each function with its results in `mutants/`, which the workflow caches, and reruns only the mutants of functions whose code changed. It finds each function's tests afresh, so a function added since Sunday gets its tests, and copies `patch/`, `assets/`, `docs/` and `test/` again. A function already marked as reached by no test keeps that until Sunday. A night with no change to `tools/` still makes every mutant and finds the tests, about three minutes on a desktop. A change to `test/unit`, `test/release.py`, the requirements, `sources.list`, or a `.S`, `.c` or `.h` file in `tools/` starts the cache afresh: mutmut keeps its old copies of those, and tests read them. The job fails under 90%, a floor under a fresh run's score: it catches a collapse, not each survivor.
- **Sundays, and by hand from the Actions tab:** everything from scratch, because a cached result can't see a change outside its own function, such as a module's constant or a function it calls. 15,920 mutants took 75 minutes on four workers of a Ryzen 7 7800X3D desktop, and 91.7% were caught (96.1% outside art.py). art.py's 2,634 take most of that time, each about 5 seconds against everything else's fraction of one. GitHub's runners are slower, so the job allows 240 minutes. Every art.py mutant runs `test_art.py`, so only the two tests that read the pane's icons draw them, the slow part, and the rest share one drawing. One of them checks the other tests' images are the shipped theme's. mutmut forks each mutant's run from a process that has already run the tests, so `conftest.py` clears every `functools` cache at the start of a session, or art's cached images would hide the mutants under them, and caps each process at 4 GB, as a mutant can loop for ever filling memory.

```sh
pip install -r requirements.txt -r test/unit/requirements.txt
mutmut run                                                  # all of tools/; needs clang, lld and llvm
mutmut run $(python3 test/unit/targets.py --since main)     # or only what a branch changes
python3 test/unit/report.py --survivors /tmp/survivors.txt  # score, table, each survivor's diff (--since as above)
```

- **Needs no stock firmware:** the fixtures in `test/unit` are synthetic, and the stock ZIP is neither fetched nor kept. A function that pins a Shanling file's hash or links against one carries `# pragma: no mutate block` on its `def` line, so it has no mutants: `compile_payload`, `patch_asset`, `compile_common`, `patch_player`, `patch_bluetoothd`, the audio module's `validate_stock` and `patch_module`, the rotator's `patch_module`, and PWM's `link`, `patch_pwm`, `patch_mcu` and `patch_bundle`. They stay with the scripts above, which need a build. A new one gets the same pragma.
- **Keep tests behind the fence:** a mutant changes a command before it runs, and `q2remote`'s commands are shell scripts for a live Q2. `test/unit/conftest.py` refuses every process but the compilers, along with sockets and signals, and hides `Q2_HOST`. `test/remote.py` runs real commands through a real shell, so it stays out of `test/unit`.
- **`build()`** carries `# pragma: no mutate block`. mutmut writes out a whole copy of a function per mutant, so its 440 lines alone made a 96 MB file that never finished generating. The pragma is on art.py's `wave()` too: only `WAVES` calls it, at import, before mutmut can switch a mutant on, so all 21 of its mutants survived.
- **Survivors are not all gaps.** Most left are equivalent (`<I` as `<i` on a word under 2^31) or machine code in `patch_bluealsa`, which only `test/bluealsa.py` can judge against a build.

### C

mutmut mutates Python only. For the C (1,158 functions added or changed since 1.2.0, 394 of them in `navigation.c`), `test/cmut` works one file at a time. `mutate.py` writes each mutant as a whole copy of the file, one token-sized change each: a comparison's neighbours, `&&` for `||`, a constant one up, one down or 0, a condition held true or false, a statement gone, a return of 0. `run.py` compiles each as its tests build it and tests only those that compile to a new object: one the compiler rejects, or that compiles to the original's or an earlier mutant's object, can't behave differently, and none of those count towards the score. A host suite's own build refusing a mutant counts as the compiler's rejection too, not a catch: `mp3_gapless.py`'s wrapper calls `mp3_trim`, which the file alone leaves unused, so it rejects a few mutants the table's flags let through. A compile or link that fails without the compiler naming a line of the source, or for want of room or memory, is the sandbox's failure: the run stops there, unanswered, and its report says it stopped short. Mutants of C run as real code, so `sandbox.sh` runs them in a container with no network, a read-only root and only a 1 GB tmpfs to write, as the fence above can't reach them.

```sh
docker build -t q2-cmut test/cmut
python3 test/cmut/mutate.py patch/radio.c /tmp/cmut/radio  # each mutant a whole copy, and manifest.jsonl saying where
CMUT_PYTHON=$pythonLocation test/cmut/sandbox.sh patch/radio.c /tmp/cmut/radio /tmp/cmut/radio.jsonl --workers 4  # rerun to resume after a stop
python3 test/cmut/report.py patch/radio.c /tmp/cmut/radio /tmp/cmut/radio.jsonl --survivors /tmp/cmut/radio.txt --copy /tmp/cmut/radio-left  # the score; each survivor as a diff
# after a new test: the survivors alone, into a fresh results file
CMUT_PYTHON=$pythonLocation test/cmut/sandbox.sh patch/radio.c /tmp/cmut/radio-left /tmp/cmut/radio-left.jsonl --workers 4
python3 test/cmut/report.py patch/radio.c /tmp/cmut/radio-left /tmp/cmut/radio-left.jsonl --survivors /tmp/cmut/radio-left.txt
```

- **Wired up:** a table in `sandbox.sh` holds each file, its test and what that test reads. `library_scope.c` and `chapters.c` run through their own scripts, which build the file themselves, with the flags the table repeats. `headset.c` and `radio.c` run through their own `test/fw/test_<name>.py` alone. Another file `test/fw` builds is one more name in the table's `test/fw` line, and its run takes longer the less of it its tests select: a test file that forks runs all its tests for every mutant, as below, so `navigation.c`'s and `playback.c`'s would.
- **`test/fw`'s files:** `test/fw/host.py` builds the library once. A mutant compiles its one file with `host.py`'s flags, its statics renamed as `host.build` renames them, and links with the other objects into a library of its own, which `conftest.py` loads instead of building one when `Q2_FW_LIBRARY` names it. `run.py` stops if that link makes a library unlike `host.build`'s, or the original compiles to other symbols. Each mutant's object waits for its test on the tmpfs while 256 MB of it is left, and is compiled again for its test after that, so a large file's mutants take longer but can't fill it.
- **Only the tests that reach it:** a test that never runs a mutant's lines sees what the original does. So `run.py` builds the original with gcov's counters and runs each test alone first, and a mutant runs only the tests that ran its lines; a line with no code of its own (a table, a `#define`'s body), a line with a `case` label, as the `switch` jumps there from tests that ran other lines, or a line no test runs, runs them all. Not yet for a test file that forks (`in_fork`): a child's counts used to end with it, unwritten; they now reach the file when the child closes the library, so `run.py` could select for those files too, once measured. pytest stops at the first failure and runs the test that killed the last mutant first, as neighbouring mutants mostly fall to the same test, once the original passes its tests backwards as well as forwards. Each run forks from a process that has already imported pytest and `host.py`, and has seconds of CPU, not of the clock, so a loaded machine can't time out a survivor.
- **`CMUT_PYTHON`:** the image's own Python can't load `test/fw` (see [Firmware tests](#firmware-tests)), so `sandbox.sh` mounts the folder `CMUT_PYTHON` names, read-only: a position-independent Python 3.12 with `requirements.txt` and `test/unit/requirements.txt` installed, as `actions/setup-python`'s (`$pythonLocation`). The host suites don't need it.
- **Killing survivors:** each survivor in the `--survivors` file is `=== <id>.c` and its diff against the file, line numbers in the `@@` header; a killed mutant's `reason` in the results names the first test that failed, or the test a crash was in. `report.py --copy` puts the survivors and their lines of the manifest in a folder of their own, so a new test runs against them alone in a minute or two; `CMUT_TEST` mounts another copy of the test in place of the file's own. Some survivors can't be killed: they change nothing a caller can see, or need a failed allocation or another thread.
- **Weekly:** `mutation.yml`'s `cmut` job mutates every wired file on Sundays, with mutmut's run from scratch, and by hand from the Actions tab, each file on a runner of its own, side by side. Each uploads its survivors and results as `c-surviving-mutants-<file>`, and fails only when its score falls under its floor in the job, a little under the score below, or its run stops short: it catches a collapse, not each survivor.

| File              | Its tests                 | Mutants | Tested | Caught | Floor | Four threads |
| ----------------- | ------------------------- | ------: | -----: | -----: | ----: | -----------: |
| `library_scope.c` | `test/library_scope.py`   |     612 |    427 |  89.0% |   87% |         58 s |
| `chapters.c`      | `test/chapters.py`        |   1,050 |    773 |  92.2% |   90% |   3 min 58 s |

The seven files then wired, `photos.c` (1,707 mutants, retired with Photos since) and `mp3_gapless.c` (2,069, retired with the stock player) among them, 13,658 in all, took 38 minutes one file after another, pinned with `CMUT_CPUS` to four threads on two cores of a Ryzen 7 7800X3D desktop, as a 4-vCPU runner's threads are, at a load average under 6, and 45 minutes before `test/fw`'s files had their survivors' tests, at a load average of 10 to 22. A runner's slower cores could take that past an hour, so the job gives each file a runner of its own and 60 minutes, against 7 for the longest here. The results' last lines add up to 7,604 seconds of the container's CPU time (`cpu_seconds`, which load from outside stretches less than the clock's). Runs with the same tests agreed on every mutant but one, in `photos.c`. What `test/fw`'s files leave alive is mostly design constants (colors, coordinates, dither tables, waits) that the tests check by relation rather than by value, and lines with no code of their own, which every test runs against. The host suites check their limits by relation too, so a mutant that moves one consistently lives: `SCOPE_MAX` one lower for both the scan and the reader, or `chapters_poll`'s reads a tick and bytes a read. `mp3_gapless.c`'s checks from the pilot's branch expect a tag frame too small for LAME's extension to be refused, which the parser now reads as a silent frame, so they stay behind and its score is the suite's as it is.

The order for the rest:

2. `coverflow.c` and the `peq*` files, through `test/coverflow.py` and `test/peq.py`, which need the 32-bit libraries.

## Coverage

Both workflows count what their stock-free runs reach and fail under a floor, and each run's summary has the table.

- **A branch's own check:** the full run is five and a half minutes, so a branch that changes a `tools/` module is held to the same `fail_under` for that module alone, by the `test/unit` files that import or name it (`tools/ci/covcheck.py`, planned by `affected.py` as `cov:tools/X.py` and run by the merge batch): [what a branch runs](#fast-test-runs).
- **`tools/`:** `tests.yml` runs `test/unit` under [coverage.py](https://coverage.readthedocs.io), every branch counted, and fails under `fail_under` in `pyproject.toml`. The functions with `# pragma: no mutate block` on their def line and the command lines are left out, so the floor is all of the rest.
- **C:** `firmware.yml` runs `test/fw` and the host suites with `test/coverage/cc` first on `PATH`: `cc` with gcov counters, which keeps each compile's counts under `$Q2_COV` when a suite deletes its build folder. [gcovr](https://gcovr.com) reads them, fails under the line and branch floors in the workflow, and uploads the per-line pages as `c-coverage`. The ASan run isn't counted. Most of `navigation.c` is `test/patch.py`'s, which needs a stock build, so it stays low here.
- **Floors:** they catch a collapse (a suite or the wrapper that stopped counting), not each change, so they sit a little under the measured figures. Raise one by hand when the measured figure is well clear of it. The host suites run only counted in CI; `test/fw` also runs plain under ASan.

```sh
pip install -r requirements.txt -r test/unit/requirements.txt gcovr==8.4
coverage run -m pytest test/unit --basetemp ~/.cache/q2-pytest/unit && coverage report  # needs clang, lld and llvm
export Q2_COV=~/.cache/q2-cov; rm -rf $Q2_COV; mkdir -p $Q2_COV  # counts add up across runs: start empty
PATH=$PWD/test/coverage:$PATH python3 -m pytest test/fw --basetemp ~/.cache/q2-pytest/fw  # and the host suites, the same way
gcovr --root . --filter patch/ --gcov-ignore-errors=source_not_found --html-details ~/.cache/c-coverage.html $Q2_COV
```
